## 作業内容
計画に基づいて、プロダクションコードの実装前にテストを作成してください。
Workflow Contextに示されたReport Directory内のレポートのみ参照してください。他のレポートディレクトリは検索・参照しないでください。契約確認に必要なリポジトリのソース、既存テスト、設定は参照できます。

**重要: プロダクションコードは作成・変更しないでください。テストファイルのみ作成可能です。**

**共通の契約経路分析**

観測可能な不変条件、その成立を保証する担当箇所、同じ原因で変更される理由が一致する経路は、物理的なコード位置、ファイルパス、症状、利用者、外部境界、最終結果が異なっても、同じ問題としてまとめて扱ってください。いずれかが異なる場合だけ、別の問題として扱ってください。

実在する経路を `owner / definition -> producer -> transform / normalize / validate -> persist / transfer / restore -> consumer -> exception / retry / fallback / parallel -> terminal / API / observability` として記述し、該当しない段階を作らないでください。

ファイル名や関数名の一覧だけを経路の根拠にしないでください。入口から各利用箇所へ値や状態が渡る呼び出し、引数、返り値、保存・復元の接続をコードで確認し、接続を確認できない候補は未確認または対象外として区別してください。

確認した経路ごとに、不変条件の成立に関与して変更が必要か、接続しているが既存契約を保持すべきか、別の不変条件または担当箇所に属するかを平易な言葉で区別してください。

この分析だけを理由に確認範囲を広げないでください。探索、指摘、編集は、現在の要求と提示された確認範囲から必要性を導けるものに限ってください。


変更した不変条件を成立させる経路と反例を、観測可能なテスト義務へ対応付けてください。テスト専用ステップでは production code を編集せず、変更対象外の既存契約を維持し、別の不変条件や担当箇所の改善へ広げないでください。

**変更契約の追跡（実装タスクでは必須）:**
1. 要求、計画、変更対象外として維持する観測可能な既存動作から、今回の完了条件を特定してください。ワークフローが契約IDを提供する場合は意味を維持し、実装箇所や作業順のためにIDを増やさないでください。
2. 後段で新しい完了義務が見つかった場合は、要求または変更した契約との因果関係を示してください。根本原因や設計を変える場合は既存IDの意味を書き換えず、再計画を要求してください。
3. 完了証拠は、各変更契約を直接観測できるテストまたは再現可能な確認結果へ対応させてください。広いテストスイートの成功だけを個別契約の証拠にしないでください。

**存続する実体の状態が変わる要求:**

要求が、特定の変化（入力、環境、設定、接続状態などの変化）を名指しし、その変化の後もその時点の状態に合わせて振る舞うことを求め、かつその変化をまたいで同じ実体（画面、プロセス、接続、セッション、キャッシュなど）が存続する場合、契約の観測単位はその実体の寿命に合わせる。既存の振る舞いを維持する要求や、変化を名指ししない要求は、それだけではこの契約にならない。
- 同じ実体の上で、変化前の状態 → 変化 → 変化後の状態を一続きに観測することを完了証拠にする。条件だけ変えて別の実体を作り直した観測は、この契約の証拠にならない
- 変化前にその実体が作った成果物（出力済みの表示、計算済みの結果、保持している一覧や接続状態など）も追従の対象に含める。変化後に新しく作るものだけを対象にし、変化前の成果物を旧状態のまま残す読み替えをしない
- 計画では、存続する実体を特定し、変化に反応できる構造か（一度だけ作る、初回だけ計算する、キャッシュする構造は反応できない）を確認する。反応できなければ、その構造の変更を計画に含める
- テストで観測できる実体を、実環境での手動確認だけに送らない。該当する契約があるのに、計画の「状態・所有権」やテスト報告の「連続実行・所有権・並行性」を「該当なし」にしない
- 変化をまたいで存続する実体がない要求（入力から出力への変換、呼び出しごとに新しく作る結果、プロセスを作り直してから読み込む永続化）や、変化を名指ししない要求には、この軸を持ち込まない

**進め方:**
1. 変える観測可能な振る舞いと、維持する既存契約を特定する
2. 契約の所有者と、その所有者を import・呼び出し・直接参照する既存テストを確認する。ファイル名やテストが名乗る目的で除外せず、各assertionを観測可能な契約へ対応付ける。対応付けられないassertionの処置は、タスクで示されたテスト関連の判断基準に従う。その基準がある場合は、全assertionに契約への対応または基準が認める更新・削除の処置が付くまで次へ進まない。基準がない場合は、観測可能な契約だけで維持・更新・削除を決められないassertionを未対応として記録する
3. 成立する振る舞いと、一部だけを満たすもっともらしい誤実装を識別する最小の入力または状態を選ぶ。契約にない保存、ライフサイクル、統合、並行性の軸を作らない
4. 契約を直接観測する最小のテストを作る。実在する主要経路が単体境界を越える場合だけ統合テストを選ぶ
5. このtest-first工程ではテストを実行し、未実装のプロダクション動作を理由に失敗することを確認して、テスト設定・fixture・assertionの欠陥と区別する。実装後の確認条件として、意図した振る舞いが成功し、選んだ誤実装が意図した理由で失敗することを記録する。mutation確認は実装後に既存の隔離runnerがある場合だけ破棄可能なコピーで行い、この工程では実行しない
6. 完了前に所有テスト群を再確認する。適用可能なテスト関連の判断基準がある場合は、契約への対応または基準が認める処置のないassertionが残っていないことを確認する。基準がない場合は未対応assertionを明示する。誤実装を拒否する入力・状態とassertionの対応、未カバー理由、実行結果を作業結果に残す


**テストの境界:**
- 観測可能な契約を基準に作成・更新・削除を判断し、タスクにテスト関連の判断基準が示されている場合はそれにも従う
- この段階では未実装による失敗を許容するが、実装後も残るテスト欠陥は修正する

**編集後セルフスキャン（必須）:**
報告の前に、今回の自分の編集が新しい問題を持ち込んでいないかを機械的に走査してください。レビュー指摘や計画の完了確認とは別の走査であり、対象は今回の編集が作った差分そのものです。
1. 未使用化の走査。今回の編集で呼び出し元・参照元を失った引数、変数、関数、export、import、型を検索で確認し、削除してください。分岐を追加・変更した場合は、全ケースが吸収された結果、到達不能になった分岐・引数・フォールバックが残っていないかも確認してください。編集の結果、全呼び出し側が同じ定数を渡すだけになった引数・オプションは役目を終えています。値を定義側へ畳み込み、引数を削除してください
2. 依存方向の確認。今回追加・変更した import ごとに、プロジェクトが宣言する層方向の規約（宣言コメント、設定、ドキュメント）に反する向きがないかを確認してください。モジュールの移動・改名・層の付け替えを行った場合は、import 文を変更していなくても向きが変わるため、そのモジュール内の全 import を確認対象にしてください。逆向きの import が必要になった場合は、そのまま追加せず、実装をどちらの層に置くべきかを見直してください
3. 追加・変更した import、export、callee、call site が属する module ごとに、対応する module mock と test double を repository 全体から検索してください。`vi.mock`、`jest.mock`、`mock.module`、provider 固有の module mock、spy、stub、fake、mock factory、fixture、共有 test helper を含めます。対応する mock または double を定義している test file はすべて確認し、変更後の signature、return shape、error 挙動、side effect を保つことを確認してください。単にその module を import する全 consumer test の総当たりにはしないでください。
4. project の test script の入口（例: `npm test -- <test-file>`）から、対応する mock または double を定義する test file と、変更した挙動を直接所有する分類済み test file（必要なら正本・共有の fix 経路を含む）を実行してください。直接 Vitest を代用したり、すべての import consumer test を要求したりしないでください。integration または heavy test を変更した場合は、分類・配線 test（`npm test -- src/__tests__/releaseVerificationWiring.test.ts`）と対象 test の両方を実行し、command、終了 status、結果を記録してください。修正によって、すでに取得済みの検証結果（build、test、記録した証拠）が無効になった場合は、該当する検証を再実行してから報告してください。
走査で見つけた問題のうち、このステップで編集が許可されている範囲のものは、この編集の中で修正してください。編集範囲外のもの（テスト専用ステップから見たプロダクションコードなど）は修正せず、報告に記録するだけにしてください。走査した module、対応する mock/double test file、変更挙動を直接所有する分類済み test file、command、結果を報告に1行で記録してください。

# 根拠に基づく判断

計画・実装・検証・レビューで、要求、観測事実、提案、未確認事項を区別して判断する。

## 原則

| 原則 | 基準 |
|------|------|
| 要求の正本 | 元要件・仕様・公開契約と、計画・報告・提案を区別する。提案は繰り返し記載されただけでは必須要件にならない |
| 双方向の確認 | 判断を支持する証拠と、否定する現在のコード・証跡の両方を確認する |
| 実在経路 | 入口から観測点まで既存の検証・中断・後片付けを含めて追跡し、実際に働く防御を取り除いた仮想経路を欠陥の根拠にしない |
| 効果と正常系 | 防御の存在だけで成立とせず、禁止された結果・副作用を防ぐタイミングと、必要な正常系の保存を確認する |
| 明示義務の保存 | 要求が方式・構造・テスト・文書まで定めていれば、結果が同じという理由で省略しない |
| 未確認の明示 | 証拠の欠如を成功にも欠陥にも読み替えず、判断できた範囲と未確認範囲を分ける |

## 判断と作業権限

- 方式が指定されていない場合は、提案への一致ではなく要求された条件の成立で判断する。現在の挙動や既存テストも、要求に反する振る舞いを正当化する根拠にはしない
- 記録がないことと、必須の実装・検証手段がないことを分ける。不足を主張する場合は、根拠となる義務、満たされていない条件、既存の実装・検証でその条件を満たせない理由を示す
- 判断に必要な情報が足りない場合は、不明な前提と、その確認に必要な情報を示す。推測で原因を確定したり、必須条件を緩めたりしない
- この原則は実行・編集権限や工程の完了条件を変更しない。実装担当に要求されたテスト実行や証跡の提出は省略せず、読み取り専用の担当は新しい実行を行わずに未確認範囲を記録する

## テスト不足の根拠

- テストを必須の追加修正とする場合は、明示された検証義務、新規・変更された振る舞いの代表的な未検証条件、または確認済み不具合の再発防止に結び付ける。新規・変更された振る舞いを根拠にする場合は、今回変更された操作・受け渡し・状態遷移と未検証条件の関係を示す。現在の実装に不具合がなくても、これらのテスト不足は修正対象になる
