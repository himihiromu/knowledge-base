- 入力・失敗条件の未検証と、同じ条件に対する観測方法の追加を分ける。新しい呼び出し元から既存処理を利用することや、その内部状態が後続操作で使われることだけで、既存処理の全状態を今回の検証義務へ広げない。既に通している条件に別の観測を必須とするなら、その観測を要求する契約、今回変更した受け渡しや更新規則、または現在確認できる不整合を示す

- 各指摘のIDと、正本に裏付けられた問題、受入条件、修正境界を維持し、指摘の根拠は現在のコードへ再照合してください。レビュアーが示した修正方法は候補として扱い、要求、仕様、schema、公開契約より優先しないでください
- 同じ原因、破られる観測可能な条件、受入条件を持つ指摘は、報告場所ごとに分断せず1つの修正として計画してください。名前、型、ファイル上の近さだけを統合の根拠にせず、原因または受入条件が異なる問題は分けてください
- 定義元から生成、変換、検証、保存、復元、利用箇所、外部から観測できる結果まで、受入条件の成立に必要な実在経路をコードとデータフローから確認してください。代表箇所だけで完了とせず、関係のない隣接契約へ範囲を広げないでください
- enum、状態遷移、入力形式、候補順序、件数上限などが問題に関係する場合は、仕様または現在のコードで適用を確認できる値と境界だけを具体化してください。根拠のない値や組み合わせを網羅項目として追加しないでください
- 各経路について、変更、移行または削除、確認のみのどれを行うかを明確にしてください。共有箇所の変更だけで条件を満たす利用側は、対称性のために編集せず確認対象としてください
- 言語、runtime、標準ライブラリ、依存ライブラリの挙動を原因または検証根拠に使う場合は、対象コード、型・API仕様、または提供された記録済み結果から実際の入力と結果を確かめてください
- テストを簡単にすることや命名を整えることだけを理由に、非公開の定義を公開したり、公開schemaやfield名を変更したり、本番用の列挙APIを追加したりしないでください
- 修正方法、検証方法、完了条件を、要求、現在のコード、公開契約へ照合してください。タスクに関係する判断基準や参考資料が示されていれば反映し、完了条件は外部から観測可能にしてください
- 検証は対象の契約経路を通り、問題が残っていれば失敗できる観測点を持たせてください。静的な条件は、現在のコード、型、schema の照合で確認してください
- 修正計画の見直しが必要なのは、原因、修正境界、必要な影響経路、修正方法、受入条件、検証方法の不足または矛盾を計画の変更で解消できる場合です。計画どおりの実装や証拠が不足しているだけの場合と区別してください

**共通の契約経路分析**

観測可能な不変条件、その成立を保証する担当箇所、同じ原因で変更される理由が一致する経路は、物理的なコード位置、ファイルパス、症状、利用者、外部境界、最終結果が異なっても、同じ問題としてまとめて扱ってください。いずれかが異なる場合だけ、別の問題として扱ってください。

実在する経路を `owner / definition -> producer -> transform / normalize / validate -> persist / transfer / restore -> consumer -> exception / retry / fallback / parallel -> terminal / API / observability` として記述し、該当しない段階を作らないでください。

ファイル名や関数名の一覧だけを経路の根拠にしないでください。入口から各利用箇所へ値や状態が渡る呼び出し、引数、返り値、保存・復元の接続をコードで確認し、接続を確認できない候補は未確認または対象外として区別してください。

確認した経路ごとに、不変条件の成立に関与して変更が必要か、接続しているが既存契約を保持すべきか、別の不変条件または担当箇所に属するかを平易な言葉で区別してください。

この分析だけを理由に確認範囲を広げないでください。探索、指摘、編集は、現在の要求と提示された確認範囲から必要性を導けるものに限ってください。


以下の不足分類は、指摘の前提と反証を照合し、正本に基づく不足を確定した項目にだけ適用してください。提案方法との差や任意の実行記録の欠如を、計画への記載の有無だけで不足に昇格させないでください。

修正担当の報告と修正計画の一覧から独立して、対象となった同じ不変条件の担当箇所と影響する全経路を再構築してください。要求・仕様・schema・型・状態遷移を正本とし、現在の定義・参照・呼び出し・データフローを使って、今回適用される有限要素、状態、入口、consumer、terminal を先に列挙してください。現在の実装を正本にできるのは、修正対象の振る舞いとは別に適用集合、状態遷移、公開契約を定義している箇所だけです。修正対象の振る舞いを、その振る舞い自身の正本にしてはいけません。正本が有限集合を定める場合は、計画に記録された要素だけを確認して終えてはいけません。

再構築した集合を計画の有界な経路と比較してください。計画の各行について不足を評価する前に、計画上の呼称を根拠にせず、上で特定した要求・仕様・schema・型・状態遷移、対象の不変条件、受入条件との照合だけで、その行が対象に属するか分類してください。

計画に含まれていても、この照合で対象外と確定した行（隣接する契約や、無変更で保存すべき境界）を、その行自体の修正対象、計画不備、実装不足、証拠不足として記録してはいけません。ただし、無変更で保存すべき境界については、修正がその境界を保存したことを確認してください。修正による破壊を検出した場合は、その行自体の不足ではなく、既存契約保存の完了義務違反として不成立・未確認事項へ必ず記録してください。

同じ不変条件と受入条件に必要な要素・状態・経路が計画から漏れていれば計画不備、計画に記録済みの義務について実装または証拠が不足していれば実装不足または証拠不足です。物理的なコード位置やファイルパスを同一性の根拠にせず、未確認の利用側は同じ不変条件に属し受入条件を満たすために必要な場合だけ含め、隣接する別契約へ広げないでください。根拠から適用を確認できない軸の組み合わせは作らないでください。

計画との比較後は、再構築した有界な集合の全行を反例で確認してください。

最終結果を返す前に、正本が定める各有限集合と状態軸をもう一度列挙し、比較表に載っていない要素・状態が残っていないことを確認してください。漏れ・不足が見つかった場合は、要素・状態ごとに1件ずつ扱い、その要素・状態が計画の有界な集合に記録されているかだけで不足の種別を判定してください。記録がなければ計画不備、記録があり実装または証拠がなければ実装不足または証拠不足として記録してください。種別の異なる不足を1つの項目または1つの finding に統合せず、片方の種別があることを理由にもう片方を省略しないでください。

計画にある各問題について、現在のコード、修正報告、検証結果が一致するか確認してください。報告に不足があれば計画とコードから確認し、不足していた理由を記録してください。報告の不足だけを計画変更の根拠にしないでください。計画した変更や証拠が不足する場合と、計画自体の前提・境界・方法・検証方法に変更が必要な場合を区別してください。テスト通過だけで完了としないでください。

品質確認の失敗を未完了または再修正の理由にする前に、次のいずれかとの因果関係を、差分、参照経路、記録済みの再現結果、または基準となる状態との比較から確認してください。

- 修正計画の受入条件が成立していない
- 今回の差分が新しい退行を生じさせた
- 今回の変更で維持すべき既存条件が壊れた

いずれかとの因果関係を確認できる失敗は、広い品質確認で見つかった場合や計画外のファイルに現れた場合でも未完了として扱ってください。因果関係を確認できない失敗は別の問題として記録し、計画した修正単位の未完了理由や再修正対象にしないでください。記録済み結果で基準となる状態にも同じ失敗があることや、変更箇所への参照経路がないことは、因果関係がないと判断する根拠にできますが、名称や推測だけで判断しないでください。


判定に独立して必要なレポート、正本、直接の呼び出し経路は、可能な限り同じ探索単位でまとめて確認してください。これは確認順序だけを定めるもので、探索範囲を広げる理由にはなりません。互いに依存しない読み取りや検索を進捗報告ごとに直列化せず、判定に不要な任意の履歴やテストの不在確認を続けないでください。必要な証拠がそろったら出力契約に沿った最終結果を返し、進捗報告だけで応答を終えないでください。

**検証手順:**
1. Report Directory の最新レビューレポートで、計画が対象とした問題、不変条件、受入条件、隣接する別問題との境界を確認する
2. 修正報告を正解表にせず、上の修正経路確認に従って正本から再導出した状態・経路と計画の比較結果を確定する
3. 再導出した対象について、不変条件・対象経路・その条件を壊す反例の対応を示し、対応ごとに完了を独立して判定する。振る舞い修正、利用側移行、旧経路削除、既存契約保存を別々に現在のコードと差分へ照合する
4. 各完了義務について、成立例だけでなく失敗例、境界値、逆方向の反例を現在のコードと記録済み証跡から追跡する。不足を見つけても最初の1件で打ち切らず、同じ前提や探索方法で完了扱いされた全修正単位へ確認を広げる
5. 静的な義務はコード照合から判定し、実行時の振る舞いは提供されたレポート、ログ、記録済み結果と現在のコードを照合する。各義務が壊れたときに既存のどの観測点で検出できるかを確認し、広いテストスイートの成功や修正報告の自己申告だけを根拠にしない。記録がない範囲は未確認とし、その欠如だけを未完了や再修正の理由にしない
6. 修正報告に記録された品質ゲートだけを確認し、記録されていないゲートを追加で要求しない
7. 計画と修正報告の不変条件を照合する。その後、出力契約に沿って更新・引き継ぎを行う
8. 実装または証拠の不足と、計画の前提・修正境界・方法・検証能力の不足を区別する。環境要因として後続確認へ分けるのは、現在のコードと記録済み証跡から実装欠陥ではないことを確認できた場合だけとする

結果の分類と必要項目は出力契約に従ってください。正本に基づく全完了義務と受入条件を独立に照合し、確認した不足がなければ成功としてください。任意の実行記録がない範囲は、成功証跡と区別して未確認として残してください。不足があれば、その根拠と修正報告の証拠が検出できなかった理由を列挙してください。


---

新しい指摘や修正対象を記録する前に、Report Directory にある最新のレビュー裁定、修正計画、修正報告、完了検証を確認してください。

- 原因、破られる観測可能な条件、受入条件が同じ指摘は同じ問題として扱い、既存の問題 ID と指摘 ID を保ったまま、今回確認した場所、経路、証拠を追加する。名前、型、ファイル上の近さだけでは同じ問題と判断しない
- 同じ原因で変更が必要な経路は、定義元から利用箇所と外部から観測できる結果まで同じ回で確認する。実在しない経路や関係のない仕組みを網羅項目として要求しない
- 修正済みとした問題が別の場所で再び確認された場合、場所ごとの新しい問題として扱わない。前回の影響範囲確認または修正が不十分だった理由を確認し、同じ問題に関係する未確認の経路を見直す
- 完了は記録の有無や件数ではなく、現在のコードで受入条件が関係する全経路に成立し、同じ確認方法で未解消箇所が残らないことを根拠に判断する
- 原因、破られる条件、受入条件のいずれかが異なる指摘は別の問題として扱う。今回の要求や既に修正対象とした問題から必要性を導けない問題を追加しない

受入条件を引き継ぐときは、出典の対象状態、操作、評価時点、観測対象、期待結果を保持してください。過去の要約や実装済みの証拠に合わせて条件を狭めないでください。複数状態の義務を一部の状態へ縮めたり、外部出力の義務を内部呼び出しの引数だけで確認済みにしたりしないでください。提案された検証手段自体を新しい要求にせず、代替手段では同じ違反を検出できる根拠を示してください。検出できない部分は未確認として残してください。
