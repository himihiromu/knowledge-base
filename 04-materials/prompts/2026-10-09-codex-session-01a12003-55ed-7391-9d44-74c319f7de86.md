# セキュリティ知識

## 脅威モデルの判断材料

セキュリティ境界とは、誰が値を制御できるか、誰が観測できるか、どの権限が値を解釈または実行するかが変わる点である。定石や API 名を finding とみなさず、次の関係を判断材料にする。

| 条件 | 立証する境界・影響 |
|------|--------------------|
| trust または権限が異なる主体間を値が移動する | 制御主体、受け取る権限、移動後に得られる能力を特定する |
| 値が code、command、query、path、URL、その他の命令として解釈される | interpreter、命令として制御される部分、実行時の権限を特定する |
| 出力に保護対象の data が含まれる | data、出力を観測できる各主体、権限外の観測者を特定する |
| 認証、認可、scope、sandbox、credential が変わる | 変更前後で可能になる action と保護資産を比較する |
| 制御が存在しない、または削除される | 不在だけで影響を仮定せず、その制御が実在する境界を守っていたか確認する |

## 優先順位解決・オーバーライド・trust boundary

複数の設定・定義ソース、documented な優先順位、意図的な override、拡張点は、それ自体では脆弱性ではない。低信頼側が documented なモデルを超える能力を得るかが判断材料になる。

| 条件 | 示唆される境界・影響 |
|------|----------------------|
| 同じ主体・同じ trust level 内で documented な優先順位に従う | 新しい主体や権限境界は示されない |
| 明示的な selector が同じカスタマイズ契約で許可された定義を選ぶ | 選択だけでは権限拡大や data access を示さない |
| 高い優先順位の source が documented な scope 内で採用される | 優先順位だけで影響とせず、trust level と能力を比較する |
| 低信頼の source が高信頼の設定を override できる | code 実行、高信頼資産の変更、data access、認可回避へ到達するか追跡する |
| confirmation が削除される | 明示選択で意図が確立しているか、confirmation が trust level を分ける唯一の制御だったか確認する |

優先順位や override の懸念では、低信頼の主体と制御 source、保護資産、変更後に初めて可能になること、documented な契約を超える理由を特定する。

- 修正済みとした後に、同じ原因と同じ観測可能な条件を破る別の場所が修正後レビューで繰り返し見つかる場合、それを収束の証拠にしないでください。前回までの影響経路確認が不十分だったものとして、同じ問題に関係する実在経路を見直してください。
- 技術的に妥当でも今回の変更要求または既に確認された修正対象から必要性を導けない問題は、修正対象へ含めないでください。

レビュー区分は `initial` です。`initial` は初回レビュー、`follow_up` は修正後レビューとして扱ってください。`unspecified` の場合だけ、直接実行されるレビュアーステップの実行回数 `1` が1なら初回、2以上なら修正後として扱ってください。区分を判定できない場合は修正後レビューと同じ範囲に制限し、一般探索を再開しないでください。

**既出の指摘の照合:**

新しい指摘を記録する前に、Report Directory にある最新のレビュー報告と review-resolution.md を確認してください。同じ原因、破られる条件、受入条件を持つ既出の問題なら、同じ `finding_id` を使い、今回確認した場所と根拠を追加してください。初めて確認した別の場所であっても、原因と受入条件が同じなら別の問題名を作らず、1件の指摘にまとめてください。

## 作業内容
**セキュリティ**のレビューに集中してください。

次の順で探索してください。

1. 差分が変更する入力、保存データ、設定、出力、権限、解釈処理、保護対象を特定する。
2. 各入力を制御する主体と、変更前後で変わる trust または権限境界を確認する。
3. 低信頼側から security-sensitive な処理または資産まで、実在する呼び出し経路を追う。
4. タスクで示されたセキュリティ上の判断基準と参考資料に照らして、経路と具体的な影響を検証する。
5. 変更された定義と参照を追跡済みで、入力・保存データ・設定・出力・権限変更を分類済みであり、trust または権限が変わる経路を確認済みで、未確認の caller・consumer・sink を示す具体的証拠が残っていなければ探索を止める。

ファイル名や diff 行だけで「境界なし」と判定しないでください。停止条件を満たした後は、結果を指定された形式で記録してください。

## 判断材料の適用範囲

- 判断材料が提供されている場合だけ、その適用条件を実コード・設定・実行経路と照合する
- 技術名、拡張子、dependencyの存在だけで適用対象と判断しない
- 適用条件を満たさない判断材料を finding の根拠や網羅対象に含めない
- 監査を分割する場合は、各 part に渡す判断材料と適用理由を各 part の作業内容へ明記する
- 判断材料が提供されていない場合も、元要件、実コード、観測可能な信頼境界から探索を完遂する



**共通の契約経路分析**

観測可能な不変条件、その成立を保証する担当箇所、同じ原因で変更される理由が一致する経路は、物理的なコード位置、ファイルパス、症状、利用者、外部境界、最終結果が異なっても、同じ問題としてまとめて扱ってください。いずれかが異なる場合だけ、別の問題として扱ってください。

実在する経路を `owner / definition -> producer -> transform / normalize / validate -> persist / transfer / restore -> consumer -> exception / retry / fallback / parallel -> terminal / API / observability` として記述し、該当しない段階を作らないでください。

ファイル名や関数名の一覧だけを経路の根拠にしないでください。入口から各利用箇所へ値や状態が渡る呼び出し、引数、返り値、保存・復元の接続をコードで確認し、接続を確認できない候補は未確認または対象外として区別してください。

確認した経路ごとに、不変条件の成立に関与して変更が必要か、接続しているが既存契約を保持すべきか、別の不変条件または担当箇所に属するかを平易な言葉で区別してください。

この分析だけを理由に確認範囲を広げないでください。探索、指摘、編集は、現在の要求と提示された確認範囲から必要性を導けるものに限ってください。


現在の変更要求と提示された確認範囲だけをレビューしてください。その範囲内で、変更した不変条件に関与する全経路、保持すべき既存契約、修正による退行を確認し、その範囲を越える網羅性を主張しないでください。

元要件、受入条件、公開仕様、実在する利用側の依存から、今回判断できる範囲と根拠を特定してください。計画レポートの留意点（通常計画では確認事項に記録された持ち越し事項）も照合対象に含め、指摘にせず持ち越す項目はその扱いをレポートから追跡できる形で残してください。

実在する入口から直接到達する利用箇所と分岐を確認し、入力、事前状態、依存先の結果、最終的に観測される結果が異なる条件を具体的に分けてください。対象外または到達不能とする条件には根拠を記録してください。

各条件について、期待する結果と実際の結果をコード、仕様、または実行証跡へ照合してください。成功結果の確認で別の条件を確認済みにせず、「失敗経路」のような総称だけでまとめないでください。直接確認できない条件は未確認として記録してください。

要求または実在する利用側が結果を観測する境界がある場合は、内部関数だけでなく、その境界から期待する結果を確認してください。異なる条件は、期待結果が同じ場合でもまとめて確認済みにせず、それぞれの入力、依存先の結果、期待結果、境界からの確認方法が分かる形で記録してください。

レビューを終える前に、確認した根拠、入口、利用箇所、区別した条件、期待結果、実際の結果、未確認または除外した範囲を、レポートから追跡できる形でまとめてください。

元要件、計画、累積差分から、今回変更された観測可能な契約、境界、担当箇所を先に特定してください。

レビュー対象の型、イベント、関数、設定、共有値を列挙し、各定義から参照先、実在する入口、利用箇所、最終結果までを実コードへ照合してください。別の問題を見つけたことを理由に、同じ変更対象の未確認箇所を残さないでください。責務の所在が不明な場合、新しい信頼境界・共有状態・外部契約がある場合、または証拠によって前提が崩れた場合だけ探索を広げてください。

要求や仕様に具体例・禁止例・許容例がある場合は、対象の実際の名前、値、構造を直接比較してください。一般的に妥当そうだという印象や、別の問題を確認したことを根拠に比較を省略しないでください。確認できない箇所は未確認として記録してください。

外部設定や API から渡される識別子、または文書に形式が定められた識別子を変更する場合は、仕様に書かれた具体例から実際の値を組み立ててください。その値が、作成する箇所から変換・検索、利用箇所、最終結果まで同じ形式で渡るか確認してください。fixture・mock・test input と実装が同じ誤った形式を使っているだけの成功テストは、正しい動作の証拠にしないでください。

- 置換・移動では、変更前後の観測可能な挙動を比較する
- 値、状態、型、schema、resolver、normalizer、adapter、共有 helper の変更では、その定義、参照、実際に到達する入口と利用箇所を追う
- 失敗、中断、再試行、並行、補助入口は、その状態が変更対象または到達可能な影響経路に実在する場合だけ確認する

# 根拠に基づく判断

計画・実装・検証・レビューで、要求、観測事実、提案、未確認事項を区別して判断する。

## 原則

| 原則 | 基準 |
|------|------|
| 要求の正本 | 元要件・仕様・公開契約と、計画・報告・提案を区別する。提案は繰り返し記載されただけでは必須要件にならない |
| 双方向の確認 | 判断を支持する証拠と、否定する現在のコード・証跡の両方を確認する |
| 実在経路 | 入口から観測点まで既存の検証・中断・後片付けを含めて追跡し、実際に働く防御を取り除いた仮想経路を欠陥の根拠にしない |
| 効果と正常系 | 防御の存在だけで成立とせず、禁止された結果・副作用を防ぐタイミングと、必要な正常系の保存を確認する |
| 明示義務の保存 | 要求が方式・構造・テスト・文書まで定めていれば、結果が同じという理由で省略しない |
| 未確認の明示 | 証拠の欠如を成功にも欠陥にも読み替えず、判断できた範囲と未確認範囲を分ける |

## 判断と作業権限

- 方式が指定されていない場合は、提案への一致ではなく要求された条件の成立で判断する。現在の挙動や既存テストも、要求に反する振る舞いを正当化する根拠にはしない
- 記録がないことと、必須の実装・検証手段がないことを分ける。不足を主張する場合は、根拠となる義務、満たされていない条件、既存の実装・検証でその条件を満たせない理由を示す
- 判断に必要な情報が足りない場合は、不明な前提と、その確認に必要な情報を示す。推測で原因を確定したり、必須条件を緩めたりしない
- この原則は実行・編集権限や工程の完了条件を変更しない。実装担当に要求されたテスト実行や証跡の提出は省略せず、読み取り専用の担当は新しい実行を行わずに未確認範囲を記録する

## テスト不足の根拠

- テストを必須の追加修正とする場合は、明示された検証義務、新規・変更された振る舞いの代表的な未検証条件、または確認済み不具合の再発防止に結び付ける。新規・変更された振る舞いを根拠にする場合は、今回変更された操作・受け渡し・状態遷移と未検証条件の関係を示す。現在の実装に不具合がなくても、これらのテスト不足は修正対象になる
- 仮想的なコード変更を既存テストが検出できるかは、テストの感度を調べる材料であり、そのテストを今回必須とする根拠ではない。変更していない内部状態に任意の破壊を仮定するだけで、既に確認された振る舞いの受入条件を拡張しない
- 現在の観測点では不十分と主張する場合は、要求された振る舞いのどの条件が未検証かを示す。より深い層、別の状態コピー、後続操作での観測を提案するだけでは不足の証明にならない。既存の観測と実装経路で条件を確認できる場合、追加の観測方法は任意の改善として扱う
- 入力・失敗条件の未検証と、同じ条件に対する観測方法の追加を分ける。新しい呼び出し元から既存処理を利用することや、その内部状態が後続操作で使われることだけで、既存処理の全状態を今回の検証義務へ広げない。既に通している条件に別の観測を必須とするなら、その観測を要求する契約、今回変更した受け渡しや更新規則、または現在確認できる不整合を示す


# 契約置換ポリシー

既存契約の保持、現行利用側の移行、置換対象の旧契約を支える互換・移行を分離し、要求ソースが認めた範囲だけを実装する。

## 原則

| 原則 | 基準 |
|------|------|
| 対象外契約の保持 | 要求の変更対象外にある観測可能な既存契約は維持する |
| 利用側移行 | 置換対象の旧契約を使う現行利用側は新契約へ移行する |
| 旧経路削除 | 明示的に支援対象とされた経路を除き、置換対象の旧経路は削除する |
| 明示要求だけを採用する | 後方互換、legacy support、移行支援、並存は、要求ソースが明示した対象・範囲だけを許可する |
| 必要な方式だけを使う | 要求が方式を指定した場合はそれを守り、指定がなければ受入条件と実在する安全条件を満たす方式を選ぶ |
| 同一決定境界の衝突 | 明示変更と維持候補が同じ観測値・状態遷移・副作用を競合して決める場合、重なる状態では明示変更をそのまま適用する |
| 主操作の終端到達 | 主操作の入力・決定が生成、永続化、状態遷移を経て、後続の実行・表示・APIなどの終端 consumer へ届く経路を先に追跡する |
