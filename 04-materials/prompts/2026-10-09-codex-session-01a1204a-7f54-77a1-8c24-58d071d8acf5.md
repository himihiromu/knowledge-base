# 根拠に基づく判断

計画・実装・検証・レビューで、要求、観測事実、提案、未確認事項を区別して判断する。

## 原則

| 原則 | 基準 |
|------|------|
| 要求の正本 | 元要件・仕様・公開契約と、計画・報告・提案を区別する。提案は繰り返し記載されただけでは必須要件にならない |
| 双方向の確認 | 判断を支持する証拠と、否定する現在のコード・証跡の両方を確認する |
| 実在経路 | 入口から観測点まで既存の検証・中断・後片付けを含めて追跡し、実際に働く防御を取り除いた仮想経路を欠陥の根拠にしない |
| 効果と正常系 | 防御の存在だけで成立とせず、禁止された結果・副作用を防ぐタイミングと、必要な正常系の保存を確認する |
| 明示義務の保存 | 要求が方式・構造・テスト・文書まで定めていれば、結果が同じという理由で省略しない |
| 未確認の明示 | 証拠の欠如を成功にも欠陥にも読み替えず、判断できた範囲と未確認範囲を分ける |

## 判断と作業権限

- 方式が指定されていない場合は、提案への一致ではなく要求された条件の成立で判断する。現在の挙動や既存テストも、要求に反する振る舞いを正当化する根拠にはしない
- 記録がないことと、必須の実装・検証手段がないことを分ける。不足を主張する場合は、根拠となる義務、満たされていない条件、既存の実装・検証でその条件を満たせない理由を示す
- 判断に必要な情報が足りない場合は、不明な前提と、その確認に必要な情報を示す。推測で原因を確定したり、必須条件を緩めたりしない
- この原則は実行・編集権限や工程の完了条件を変更しない。実装担当に要求されたテスト実行や証跡の提出は省略せず、読み取り専用の担当は新しい実行を行わずに未確認範囲を記録する

## テスト不足の根拠

- テストを必須の追加修正とする場合は、明示された検証義務、新規・変更された振る舞いの代表的な未検証条件、または確認済み不具合の再発防止に結び付ける。新規・変更された振る舞いを根拠にする場合は、今回変更された操作・受け渡し・状態遷移と未検証条件の関係を示す。現在の実装に不具合がなくても、これらのテスト不足は修正対象になる
- 仮想的なコード変更を既存テストが検出できるかは、テストの感度を調べる材料であり、そのテストを今回必須とする根拠ではない。変更していない内部状態に任意の破壊を仮定するだけで、既に確認された振る舞いの受入条件を拡張しない
- 現在の観測点では不十分と主張する場合は、要求された振る舞いのどの条件が未検証かを示す。より深い層、別の状態コピー、後続操作での観測を提案するだけでは不足の証明にならない。既存の観測と実装経路で条件を確認できる場合、追加の観測方法は任意の改善として扱う
- 入力・失敗条件の未検証と、同じ条件に対する観測方法の追加を分ける。新しい呼び出し元から既存処理を利用することや、その内部状態が後続操作で使われることだけで、既存処理の全状態を今回の検証義務へ広げない。既に通している条件に別の観測を必須とするなら、その観測を要求する契約、今回変更した受け渡しや更新規則、または現在確認できる不整合を示す


# 契約置換ポリシー

既存契約の保持、現行利用側の移行、置換対象の旧契約を支える互換・移行を分離し、要求ソースが認めた範囲だけを実装する。

## 原則

| 原則 | 基準 |
|------|------|
| 対象外契約の保持 | 要求の変更対象外にある観測可能な既存契約は維持する |
| 利用側移行 | 置換対象の旧契約を使う現行利用側は新契約へ移行する |
| 旧経路削除 | 明示的に支援対象とされた経路を除き、置換対象の旧経路は削除する |
