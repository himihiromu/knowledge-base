# ユニットテスト知識

## テストダブルの使い分け

テストダブルは目的に応じて使い分ける。過剰なモックはテストの信頼性を下げる。

| 種類 | 目的 | 使用場面 |
|------|------|---------|
| Stub | 固定値を返す | 外部依存の出力を制御したい |
| Mock | 呼び出しを検証する | メソッド呼び出しの有無・引数を確認したい |
| Spy | 実装を残しつつ呼び出しを記録 | 副作用の検証をしたい |
| Fake | 簡易的な実装 | インメモリDBなど軽量な代替が必要 |

### モック粒度の判断

- テスト対象の直接の依存のみモックする（間接依存はモックしない）
- 「モックが多すぎる」はテスト対象の設計の問題を示唆する
- 純粋関数は依存がないのでモック不要

```typescript
// 避ける例: 内部実装をモック（振る舞いではなく実装を検証している）
vi.spyOn(service, 'privateMethod')
service.execute()
expect(service.privateMethod).toHaveBeenCalled()

// 例: 外部依存をモックし、振る舞いを検証
const repository = { findById: vi.fn().mockResolvedValue(user) }
const service = new UserService(repository)
const result = await service.getUser('id')
expect(result).toEqual(user)
```

## テストダブルの契約一致

builder、runner、adapter、provider などをテストダブルに置き換える場合、型だけでなく本番実装の意味契約を揃える。テストダブルが簡略化してよいのは、対象テストで観測しない責務に限る。

| 観点 | 確認内容 |
|------|----------|
| 戻り値 | 必須値、任意値、欠落値、部分成功の shape が本番と一致している |
| 入力伝播 | override、context、options など、本番が分岐に使う入力を受け取り検証できる |
| 制約 | 権限、能力、tool 制限、上限値などが本番と同じ意味で渡る |
| 副作用 | セッション更新、イベント発行、保存、破棄などの有無を観測できる |
| 簡略化範囲 | テストダブルで証明できない挙動を、テスト名や期待値で主張しない |

テストダブルが本番契約の一部を省略する場合、テストはその省略範囲に依存しない振る舞いだけを検証する。権限伝播、状態遷移、欠落値処理を確認するテストでは、省略されたフィールド自体がバグの温床になる。

## 境界値分析

境界値と同値分割はユニットテストの基本手法。

| 手法 | 内容 |
|------|------|
| 同値分割 | 入力を等価なグループに分け、各グループから1つずつテスト |
| 境界値分析 | 同値クラスの境界でテスト（境界、境界±1） |

```typescript
// 避ける例: 正常系のみ
test('validates age', () => {
  expect(validateAge(25)).toBe(true)
})

// 例: 境界値を含む
test('validates age at boundaries', () => {
  expect(validateAge(0)).toBe(true)    // 下限
  expect(validateAge(-1)).toBe(false)  // 下限-1
  expect(validateAge(150)).toBe(true)  // 上限
  expect(validateAge(151)).toBe(false) // 上限+1
})
```

- 修正済みとした後に、同じ原因と同じ観測可能な条件を破る別の場所が修正後レビューで繰り返し見つかる場合、それを収束の証拠にしないでください。前回までの影響経路確認が不十分だったものとして、同じ問題に関係する実在経路を見直してください。
- 技術的に妥当でも今回の変更要求または既に確認された修正対象から必要性を導けない問題は、修正対象へ含めないでください。

レビュー区分は `follow_up` です。`initial` は初回レビュー、`follow_up` は修正後レビューとして扱ってください。`unspecified` の場合だけ、直接実行されるレビュアーステップの実行回数 `1` が1なら初回、2以上なら修正後として扱ってください。区分を判定できない場合は修正後レビューと同じ範囲に制限し、一般探索を再開しないでください。

テスト追加の指摘は、今回の変更が壊し得る受入条件または観測可能な契約と、既存テストでは検出できない具体的な失敗経路を示せる場合だけ報告してください。重複テスト、workflow名・自然言語全文・raw YAML構造・helper・内部実装詳細を固定するassert、既存loader・gate・上位behavior testで包含済みのassert、migration inventoryの恒久固定、実害や回帰検出能力のないassert追加は要求しないでください。既存テストの削減・統合候補は、今回の変更に因果関係がなければ別の問題として報告しないでください。

## 修正後レビューの判断理由

既出のテスト不足を継続または解消すると判断する前に、元要件・裁定だけから条件を抽出し、次の表で現在の証拠へ照合してください。レビュー報告は検証対象の主張であり、要求を確定する出典ではありません。レビュー報告だけに現れる条件はこの表へ入れず、後述の追加要求として扱ってください。各行の出典に、その対象・入力・評価時点・期待結果が実際に書かれているか確認してください。

**条件照合の作業表:**
```markdown
| 元要件・裁定の出典 | 対象となる操作・状態とその所有者 | 入力・前提 | 評価時点と期待結果 | 現在のテスト・実装経路の証拠 | 充足／未達とその理由 |
|---|---|---|---|---|---|
```

指摘を継続する場合は、この表のどの元条件が未達かを特定してください。元条件が充足している場合、追加の観測方法をその行の未達理由へ混ぜず、次の追加要求として別に判断してください。

**追加要求の根拠:** レビュー報告が別の観測や操作を要求している場合は、元の条件から何が増えたかを示してください。その追加分について、明示的な検証義務、今回変更された振る舞いの代表的な未検証条件、確認済み不具合の再発防止のどれに該当するかを、レビュー報告自身の主張とは独立した要件・差分・現在のコードから確認してください。

追加要求を不採用にする場合も、想定された不整合が現在の実装で起こるかを確認してください。該当操作が実行される条件と、対象の入力・経路がその条件に該当するかを、コードの出典付きで記録してください。確認できないことを、不整合が存在しない根拠にしないでください。

この照合で残った必須の不足だけを修正対象にしてください。既存テストが仮想的な変更を検出できないという説明を、追加要求の必須根拠へ置き換えないでください。元の義務が満たされ、追加分の必須根拠がない場合は、その理由で既出指摘を解消済みとしてください。



**共通の契約経路分析**

観測可能な不変条件、その成立を保証する担当箇所、同じ原因で変更される理由が一致する経路は、物理的なコード位置、ファイルパス、症状、利用者、外部境界、最終結果が異なっても、同じ問題としてまとめて扱ってください。いずれかが異なる場合だけ、別の問題として扱ってください。

実在する経路を `owner / definition -> producer -> transform / normalize / validate -> persist / transfer / restore -> consumer -> exception / retry / fallback / parallel -> terminal / API / observability` として記述し、該当しない段階を作らないでください。

ファイル名や関数名の一覧だけを経路の根拠にしないでください。入口から各利用箇所へ値や状態が渡る呼び出し、引数、返り値、保存・復元の接続をコードで確認し、接続を確認できない候補は未確認または対象外として区別してください。

確認した経路ごとに、不変条件の成立に関与して変更が必要か、接続しているが既存契約を保持すべきか、別の不変条件または担当箇所に属するかを平易な言葉で区別してください。

この分析だけを理由に確認範囲を広げないでください。探索、指摘、編集は、現在の要求と提示された確認範囲から必要性を導けるものに限ってください。


現在の変更要求と提示された確認範囲だけをレビューしてください。その範囲内で、変更した不変条件に関与する全経路、保持すべき既存契約、修正による退行を確認し、その範囲を越える網羅性を主張しないでください。

元要件、受入条件、公開仕様、実在する利用側の依存から、今回判断できる範囲と根拠を特定してください。計画レポートの留意点（通常計画では確認事項に記録された持ち越し事項）も照合対象に含め、指摘にせず持ち越す項目はその扱いをレポートから追跡できる形で残してください。

実在する入口から直接到達する利用箇所と分岐を確認し、入力、事前状態、依存先の結果、最終的に観測される結果が異なる条件を具体的に分けてください。対象外または到達不能とする条件には根拠を記録してください。

各条件について、期待する結果と実際の結果をコード、仕様、または実行証跡へ照合してください。成功結果の確認で別の条件を確認済みにせず、「失敗経路」のような総称だけでまとめないでください。直接確認できない条件は未確認として記録してください。

要求または実在する利用側が結果を観測する境界がある場合は、内部関数だけでなく、その境界から期待する結果を確認してください。異なる条件は、期待結果が同じ場合でもまとめて確認済みにせず、それぞれの入力、依存先の結果、期待結果、境界からの確認方法が分かる形で記録してください。

レビューを終える前に、確認した根拠、入口、利用箇所、区別した条件、期待結果、実際の結果、未確認または除外した範囲を、レポートから追跡できる形でまとめてください。

# テストポリシー

以下の5条件の証拠ゲートを満たす場合に限り、観測可能な振る舞いの変更には既存テストでは検出できない回帰を防ぐ最小限のテストが必要であり、バグ修正には変更前の失敗を検出できる既存または新規のリグレッションテストが必要。

## 原則

| 原則 | 基準 |
|------|------|
| Given-When-Then | テストは3段階で構造化する |
| 1テスト1概念 | 複数の関心事を1テストに混ぜない |
| 振る舞いを検証 | 実装の詳細ではなく振る舞いをテストする |
| 内部構造を契約化しない | 行数・ソース文言・import・helper名・ファイル配置・runtime freeze・参照同一性を、観測可能な契約の代用品にしない |
| 独立性 | 他のテストや実行順序に依存しない |
| 再現性 | 時間やランダム性に依存せず、毎回同じ結果 |
| 非実行資産を固定しない | 実行時の振る舞いを定義しない本文や章構成を CI の失敗条件にしない |
| 配布定義を複製しない | 同梱された宣言的資産の具体的な定義をテストの期待値へ丸写ししない |
| 否定契約を観測単位で検証 | 禁止・拒否・非継承・非対応は、完全一致文字列の不在だけで合格にしない |
| モック契約一致 | 外部SDK・APIのモックは実契約と一致させ、誤った前提をテストで固定しない |

内部構造だけを固定する既存テストは、別の内部構造テストへ置換せず削除する。削除対象の確認は変更契約の所有者を import・呼び出し・直接参照する既存テスト群に限定し、ファイル名やテストが名乗る目的では除外せず、無関係なテスト群の全体掃除へ広げない。実在する外部契約や回帰リスクがある場合だけ、その観測可能な振る舞いを検証する。文字列自体が CLI、プロトコル、公開エラーコードなどの契約である場合は完全一致を使用できる。

テスト追加を必須にするには、次の5点をすべて示す必要がある。

1. 今回その検証を追加する義務。明示的な検証要件、検証対象の振る舞い・条件自体の追加や変更、確認済み不具合のいずれかに基づく
2. 正本となる受入条件または観測可能な契約
3. 実在する経路で起こり得る具体的な失敗
4. 既存テストではその失敗を検出できない根拠
5. 検証を所有する最小レイヤー

1点でも示せない場合はテスト追加を要求しない。モジュール数、呼び出しチェーンの長さ、内部分岐数、ファイル配置だけを追加根拠にしてはならない。同じ失敗を既存の unit、integration、E2E のいずれかで検出できる場合、別レイヤーや consumer ごとの重複テストを追加しない。

検証追加の義務は、観測しようとする契約の所有者と条件に対して判断する。新しい利用側が既存部品を呼ぶことは、利用側の受け渡しや結果を検証する根拠にはなるが、未変更の既存部品内部の別条件を新たに検証する義務にはならない。要件に既存契約の維持が書かれているだけでは、既存のテスト不足を今回の必須修正へ移さない。明示的なテスト要求、変更された受け渡し・更新規則、または確認済みの不整合がある場合は、その対象条件を検証する。

## カバレッジ基準

| 対象 | 基準 |
|------|------|
| 新しい観測可能な振る舞い | 既存テストで回帰を検出できない場合、契約所有者の最小レイヤーにテスト必須 |
| バグ修正 | 変更前の失敗を検出できる既存または新規のリグレッションテスト必須。既存テストで十分なら追加不要 |
