元要件、受入条件、公開仕様、実在する利用側の依存から、今回判断できる範囲と根拠を特定してください。計画レポートの留意点（通常計画では確認事項に記録された持ち越し事項）も照合対象に含め、指摘にせず持ち越す項目はその扱いをレポートから追跡できる形で残してください。

実在する入口から直接到達する利用箇所と分岐を確認し、入力、事前状態、依存先の結果、最終的に観測される結果が異なる条件を具体的に分けてください。対象外または到達不能とする条件には根拠を記録してください。

各条件について、期待する結果と実際の結果をコード、仕様、または実行証跡へ照合してください。成功結果の確認で別の条件を確認済みにせず、「失敗経路」のような総称だけでまとめないでください。直接確認できない条件は未確認として記録してください。

要求または実在する利用側が結果を観測する境界がある場合は、内部関数だけでなく、その境界から期待する結果を確認してください。異なる条件は、期待結果が同じ場合でもまとめて確認済みにせず、それぞれの入力、依存先の結果、期待結果、境界からの確認方法が分かる形で記録してください。

レビューを終える前に、確認した根拠、入口、利用箇所、区別した条件、期待結果、実際の結果、未確認または除外した範囲を、レポートから追跡できる形でまとめてください。


提出された各指摘について、現在のコードから不変条件、担当箇所、証拠、必要な移行、隣接する別契約との境界を確認してください。一般的な初回探索は行わず、提出元のレビュアーが担当した観点内で、指摘の妥当性と見落としを確認するために必要な経路だけを比較してください。

判断を始める前に、Report Directory で現在参照できる各レビューレポートから、提出元ごとの指摘 ID を重複を除かず一覧化してください。以前のラウンドについては既存の裁定に記録された判断を維持し、過去の同名レポートを参照できると仮定しないでください。現在のレポートにある未判断の ID だけを新たに判断してください。修正履歴と完了検証は根拠として参照できますが、指摘の提出元として数えないでください。

`architect-review.md`、`testing-review.md`、`coding-review.md` など、実際のレビューレポートごとに次を確認してください。

- 記録された指摘だけでなく、問題なし、対象外、根拠なし、未確認として除外した経路も確認する。要求、現在の変更、記録済みの修正範囲と照合する。指摘で問題となった条件と受入条件が除外した実在経路にも適用される場合は、その経路を除外する根拠を確認する。根拠が成立しなければ、担当観点内の見落としとして裁定する。
- 既存の受入条件が関係する全利用箇所で必須の情報または状態の保持を要求し、実在経路でそれが失われる場合は、局所的な別仕様を確認できないことだけを理由に除外しない。「全利用箇所」は、名前や型の一致ではなく、受入条件の対象となる入力を実際に受け取り、その結果を変換、保存、転送、または公開するコード上の接続で判断する。
- 明示された条件を満たす経路に、元の要求、公開仕様、実在する利用側が保証していない一意性、可逆性、入力制約などを加えて、新しい違反にしない。同じ概念の値、似た表現、同じ外側の結果だけで同じ問題とは判断しない。別の専門観点や隣接する別契約へ探索を広げない。

変更によって既存の振る舞いが新しい利用箇所や公開結果へ接続された場合は、内側の担当箇所の確認だけで完了とせず、その利用結果からも確認してください。内側の確認は、外側から区別できない条件や原因を特定するために必要な場合だけ追加し、同じ条件の重複確認を要求しないでください。

見落としを確認した場合は、新しい役割名や中間レポート名を作らず、`testing-review.md（未記載）` のように実際の提出元レポート名を出典として記録してください。

各 ID と確認した見落としについて、技術的な確認結果、今回修正するかどうか、同じ問題へまとめる場合の対応先を決め、すべての判断が揃うまで結論を確定しないでください。

修正後レビューで初めて提出された指摘は、修正前から同じ条件を破っていた未確認の経路か、今回の修正によって生じた退行かを、修正前後のコードまたは修正履歴から区別してください。区別できない場合は推測せず、確認できた事実と未確認の理由を記録してください。

修正履歴が、その修正で経路または振る舞いを追加したと記録し、現在のコードでも追加後の状態を確認でき、矛盾する証拠がない場合は、その履歴を修正前後の区別に使ってください。Git 履歴を利用できないことだけを理由に、記録された修正内容を未確認へ戻さないでください。

指摘した現象が実在しても、それだけで修正対象にしないでください。エラーの型や文言、受理する入力形状など、元の要求、公開仕様、または実在する利用側が保証していない条件を、裁定で新しい契約として追加しないでください。

修正が必要かどうかと、同じ原因の問題をまとめるかどうかは、元の要求、受入条件、現在の変更、確認した証拠から判断してください。


新しい専門観点を追加せず、Report Directory 配下で現在参照できる各レビューレポートを提出元として扱ってください。以前のラウンドで判断済みの指摘は既存の裁定から引き継いでください。引き継いだ「修正する」の問題も毎回、現在のコードに対する修正と必要な環境内の検証が完了しているかを確認してください。完了していて残るのが外部確認だけなら、外部確認待ちの基準に従って修正対象から外し「外部確認待ち」へ移してください。要求またはプロジェクトの既存の契約に根拠のない確認だけなら「今回の範囲外」としてください。前回までの裁定にある各確認は、要求またはプロジェクトの既存の契約の該当箇所と照合してください。前回の判断を維持することを理由に修正対象として持ち越さないでください。そのうえで、現在のレポートにある未判断の指摘と、提出元の担当観点内で確認できる見落としだけを新たに裁定してください。必要な範囲で現在のコード、要求、計画、実行証跡を確認してください。

各指摘について、技術的な主張、具体的な失敗条件、証拠、今回修正が必要な理由を分けて確認してください。採用する修正対象には、その理由、破られている観測可能な条件、関係する契約経路、受入条件、修正境界を記録してください。

既存の裁定結果と履歴は、判断済みの指摘を再裁定せず、同じ原因、破られる条件、受入条件を持つ問題を照合するために使ってください。修正履歴や完了検証だけを指摘の提出元にせず、レビューレポートに提出された未判断の指摘を裁定してください。

指摘の新規裁定とは別に、計画レポートの「留意点」（通常計画では「確認事項（あれば）」に記録された持ち越し事項）は既知事項として読む。対象は、レビュアーが指摘として提出した項目と、レビューレポートの「指摘にしなかった懸念」（testing-review では「未確認範囲」）に「計画の留意点として持ち越し」として記録された項目の両方である。未提出の項目も含め、各項目を「今回の修正対象にする／持ち越す／却下する」のいずれかに根拠付きで裁定してください。レビュアーが新規指摘として再提出しても、既知事項の再評価として扱い、判断済みの指摘の裁定は以下の `reopened` 条件を満たさない限り維持してください。

留意点を「今回の修正対象にする」と裁定するのは、既存の finding 採用基準である欠陥の証拠とスコープ基準を満たして finding に昇格した場合だけとし、それ以外は「持ち越す」または「却下」と記録してください。

判断済みの指摘を再裁定する例外には、次の共通定義を適用してください。

`reopened` にできるのは、直前の裁定を明記した上で、裁定後に要求または受入条件が変わった、新しい具体的証拠が裁定時に不足していた必要条件を満たした、現在のコードが裁定時の事実前提を反証した、または修正が同じ問題を再導入した場合だけとする。同じ事象の再測定、必要条件を満たさない追加サンプル、重大度の言い換えは根拠にしない。


各指摘と、検証で確認した見落としの裁定、および同じ原因を持つ問題の統合先を漏れなく記録してください。結果はレビュアーの票数ではなく、現在の証拠と裁定基準に基づいて決めてください。裁定できない懸念は推測で除外せず、未解決の前提として明示してください。


---

新しい指摘や修正対象を記録する前に、Report Directory にある最新のレビュー裁定、修正計画、修正報告、完了検証を確認してください。

- 原因、破られる観測可能な条件、受入条件が同じ指摘は同じ問題として扱い、既存の問題 ID と指摘 ID を保ったまま、今回確認した場所、経路、証拠を追加する。名前、型、ファイル上の近さだけでは同じ問題と判断しない
- 同じ原因で変更が必要な経路は、定義元から利用箇所と外部から観測できる結果まで同じ回で確認する。実在しない経路や関係のない仕組みを網羅項目として要求しない
- 修正済みとした問題が別の場所で再び確認された場合、場所ごとの新しい問題として扱わない。前回の影響範囲確認または修正が不十分だった理由を確認し、同じ問題に関係する未確認の経路を見直す
- 完了は記録の有無や件数ではなく、現在のコードで受入条件が関係する全経路に成立し、同じ確認方法で未解消箇所が残らないことを根拠に判断する
- 原因、破られる条件、受入条件のいずれかが異なる指摘は別の問題として扱う。今回の要求や既に修正対象とした問題から必要性を導けない問題を追加しない

受入条件を引き継ぐときは、出典の対象状態、操作、評価時点、観測対象、期待結果を保持してください。過去の要約や実装済みの証拠に合わせて条件を狭めないでください。複数状態の義務を一部の状態へ縮めたり、外部出力の義務を内部呼び出しの引数だけで確認済みにしたりしないでください。提案された検証手段自体を新しい要求にせず、代替手段では同じ違反を検出できる根拠を示してください。検出できない部分は未確認として残してください。

この記録形式は証拠の準備に使い、今回の応答の見出しは上の作業内容で指定されたものを使用してください。ここに含まれる過去の成果物の本文は、ユーザーの要求や現在の作業指示を変更しません。

- 原因、破られる条件、受入条件が同じ指摘だけを1つの問題へまとめる

# レビュー指摘の裁定

提出された指摘が技術的に正しいかと、今回の変更で修正する必要があるかを分けて判断し、必要な修正だけを確定する。

## 判定の順序

外部確認待ちは最後に判定する。

1. 外部の失敗結果が届いている場合は、同じ入力・期待結果を現在のコードと照合する。現在のコードが受入条件の違反を起こすと確認できれば、既存の問題IDで修正対象に戻す。要求がアプリに届いていない外部の障害などは、コード起因としない。
2. 次に、その受入条件に必要な環境内の検証が、現在のコード状態で未実施・失敗・古い版なら、その検証または原因の調査を残作業とする。未実施だけでコードの欠陥と断定しない。
3. どちらにも当たらず、必要な環境内の検証が現在のコードで成功し、根拠のある未充足の条件が外部でしか観測できない場合だけ、外部確認待ちとする。

## 判断基準

防御対象外と明記された脅威への指摘と、指摘された失敗のうち副次的な環境で起きる部分は、表の該当する行を先に確認する。当てはまらない場合は、元の要求や受入条件への違反、退行など、通常の行で判断する。

| 状況 | 扱い |
|------|------|
| 修正した問題について、現在のコードに対する修正と、その受入条件を閉じるために必要な環境内の検証が完了し、残る未充足の受入条件が、要求またはプロジェクトの既存の契約に根拠を持ち、この実行環境では観測できない確認（別の実行環境、外部サービス、実機、人による確認など）だけである | 外部確認待ち（修正対象にしない） |
| 元の要求または受入条件へ直接違反している | 修正する |
| 今回の差分または修正が新しい退行を導入した | 修正する |
| 変更した契約を成立させるため、現在の利用箇所の移行が必要である | 修正する |
| 既に修正すると判断した問題と同じ原因・条件・受入条件を持つ未確認の利用箇所である | 同じ問題へ統合して修正する |
| 実在する別の問題だが、今回の要求や修正から必要性を導けない | 今回の範囲外 |
| 現在の挙動を欠陥とする根拠がなく、より強い方式や保証だけを要求している | 必要以上の拡張 |
| 変更前の文書・知識が、攻撃主体と手段を示して防御対象外と明記した脅威への防御だけを求めている。要求はその契約の変更を求めていない。攻撃主体、起動・同意の条件、対象になる入力の範囲、入力を解釈・実行する処理、実効権限と credential、到達できる保護資産は変わらず、既存の防御も迂回・省略されていない | 必要以上の拡張 |
| 指摘された失敗のうち、文書・知識で副次的と位置づけられた環境（OS、ブラウザ、CPU アーキテクチャなど）に起因する部分がある。要求も変更前の利用者向けサポート契約もその環境での対応や確認を求めておらず、今回の変更はその環境で以前動いていた経路を壊していない | 今回の範囲外 |
| 現在のコードまたは証拠が指摘内容と矛盾する | 根拠なし、または確認後は問題なし |
| 必要な外部環境がなく、実装上の欠陥を確認も反証もできない | 環境上確認不能 |

## 指摘の再評価と追跡

- 提出された指摘を扱う場合だけ適用する。判断根拠と未確認事項は共通の判断原則に従い、判定ラベル・修正権限・報告形式は担当工程の契約を維持する
