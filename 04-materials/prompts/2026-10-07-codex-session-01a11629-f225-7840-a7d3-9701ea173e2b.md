## 未解決の前提

- なし。最新レポートの除外項目と指定された2ファイルを照合し、今回の要求範囲内に追加修正が必要な問題は確認されませんでした。テストは未実施ですが、修正報告では文書変更として記録され、提示された受入条件では必須とされていません。

**充足判定の深さ:**

要件の充足は、要求された結果がコード上で実際に成立する経路を確認して判定してください。検証・保存・伝播を行う関数の呼び出しが存在するだけでは根拠になりません。呼び出し箇所を充足の根拠にする場合は、要求された結果に関係する呼び出し先を開き、要求された入力から観測可能な結果(保存先のパス、出力の形式、後続への伝播)まで必要な経路が繋がっていることを file:line で確認してください。開いて確認していないファイルを根拠に使ってはいけません。コード上で確認できる経路を未確認のまま充足としてはいけません。現在のコードと現在のレビュー裁定だけで判定できない要件は、下記の REJECT / BLOCKED 条件に従って扱ってください。

1. 元要件を独立に判定できる最小単位へ分解し、現在のコードへ対応付ける
2. 前段の問題は元の受入条件へ戻って解消状態を確認する
3. 未充足要件または未解消の問題があれば、修正対象、受入条件、最小の修正境界を記録する
4. 現在のコードと現在のレビュー裁定だけでは要件を判定できず、必要な外部判断または情報をタスク範囲のコード変更で得られない場合だけ、外部要因による停止として扱う

テスト・ビルドを含む機械ゲートの実行状況、結果、ログは、品質ゲートの名目でも要件充足の名目でも要求・審査しないでください。その欠如を、修正または外部入力が必要だとする根拠にしてはいけません。

**共有のレビュー裁定レポートに「外部確認待ち」がある場合だけ:**

現在の裁定レポートの各項目について、要求上の根拠と、その問題に必要な環境内の検証の完了状態を読んでください。テスト・ビルドの実行状況、結果、ログを再審査せず、裁定レポートに記録された完了状態だけをこの扱いの判定材料にしてください。

要求上の根拠が記録され、当該問題の検証が完了と記録されている外部確認待ちは、REJECT の修正対象にしないでください。それ以外の要件がすべて充足し、前段の問題も解消していて、外部確認待ちだけが残る場合は BLOCKED とし、各問題の未確認の受入条件、要求上の根拠、確認先と方法、確定に必要な証拠を記録してください。

要求上の根拠が記録されていない、または裁定レポートが当該問題の検証を未完了と記録している項目は、外部確認待ちとして扱わず通常の判定に従ってください。外部確認待ちというラベルだけで未充足要件や未解消の問題を免除しないでください。

裁定レポートに記録された「この環境で完了した修正と検証」と対象のコード状態を、最終検証レポートの外部確認待ちの表へ転記してください。


判定結果、根拠、必要な修正対象を漏れなく記録してください。

- 修正済みとした問題が別の場所で再び確認された場合、場所ごとの新しい問題として扱わない。前回の影響範囲確認または修正が不十分だった理由を確認し、同じ問題に関係する未確認の経路を見直す
- 完了は記録の有無や件数ではなく、現在のコードで受入条件が関係する全経路に成立し、同じ確認方法で未解消箇所が残らないことを根拠に判断する
- 原因、破られる条件、受入条件のいずれかが異なる指摘は別の問題として扱う。今回の要求や既に修正対象とした問題から必要性を導けない問題を追加しない

受入条件を引き継ぐときは、出典の対象状態、操作、評価時点、観測対象、期待結果を保持してください。過去の要約や実装済みの証拠に合わせて条件を狭めないでください。複数状態の義務を一部の状態へ縮めたり、外部出力の義務を内部呼び出しの引数だけで確認済みにしたりしないでください。提案された検証手段自体を新しい要求にせず、代替手段では同じ違反を検出できる根拠を示してください。検出できない部分は未確認として残してください。

# 根拠に基づく判断

計画・実装・検証・レビューで、要求、観測事実、提案、未確認事項を区別して判断する。

## 原則

| 原則 | 基準 |
|------|------|
| 要求の正本 | 元要件・仕様・公開契約と、計画・報告・提案を区別する。提案は繰り返し記載されただけでは必須要件にならない |
| 双方向の確認 | 判断を支持する証拠と、否定する現在のコード・証跡の両方を確認する |
| 実在経路 | 入口から観測点まで既存の検証・中断・後片付けを含めて追跡し、実際に働く防御を取り除いた仮想経路を欠陥の根拠にしない |
| 効果と正常系 | 防御の存在だけで成立とせず、禁止された結果・副作用を防ぐタイミングと、必要な正常系の保存を確認する |
| 明示義務の保存 | 要求が方式・構造・テスト・文書まで定めていれば、結果が同じという理由で省略しない |
| 未確認の明示 | 証拠の欠如を成功にも欠陥にも読み替えず、判断できた範囲と未確認範囲を分ける |

## 判断と作業権限

- 方式が指定されていない場合は、提案への一致ではなく要求された条件の成立で判断する。現在の挙動や既存テストも、要求に反する振る舞いを正当化する根拠にはしない
- 記録がないことと、必須の実装・検証手段がないことを分ける。不足を主張する場合は、根拠となる義務、満たされていない条件、既存の実装・検証でその条件を満たせない理由を示す
- 判断に必要な情報が足りない場合は、不明な前提と、その確認に必要な情報を示す。推測で原因を確定したり、必須条件を緩めたりしない
- この原則は実行・編集権限や工程の完了条件を変更しない。実装担当に要求されたテスト実行や証跡の提出は省略せず、読み取り専用の担当は新しい実行を行わずに未確認範囲を記録する

## テスト不足の根拠

- テストを必須の追加修正とする場合は、明示された検証義務、新規・変更された振る舞いの代表的な未検証条件、または確認済み不具合の再発防止に結び付ける。新規・変更された振る舞いを根拠にする場合は、今回変更された操作・受け渡し・状態遷移と未検証条件の関係を示す。現在の実装に不具合がなくても、これらのテスト不足は修正対象になる
- 仮想的なコード変更を既存テストが検出できるかは、テストの感度を調べる材料であり、そのテストを今回必須とする根拠ではない。変更していない内部状態に任意の破壊を仮定するだけで、既に確認された振る舞いの受入条件を拡張しない
- 現在の観測点では不十分と主張する場合は、要求された振る舞いのどの条件が未検証かを示す。より深い層、別の状態コピー、後続操作での観測を提案するだけでは不足の証明にならない。既存の観測と実装経路で条件を確認できる場合、追加の観測方法は任意の改善として扱う
- 入力・失敗条件の未検証と、同じ条件に対する観測方法の追加を分ける。新しい呼び出し元から既存処理を利用することや、その内部状態が後続操作で使われることだけで、既存処理の全状態を今回の検証義務へ広げない。既に通している条件に別の観測を必須とするなら、その観測を要求する契約、今回変更した受け渡しや更新規則、または現在確認できる不整合を示す


# 契約置換ポリシー

既存契約の保持、現行利用側の移行、置換対象の旧契約を支える互換・移行を分離し、要求ソースが認めた範囲だけを実装する。

## 原則

| 原則 | 基準 |
|------|------|
| 対象外契約の保持 | 要求の変更対象外にある観測可能な既存契約は維持する |
| 利用側移行 | 置換対象の旧契約を使う現行利用側は新契約へ移行する |
| 旧経路削除 | 明示的に支援対象とされた経路を除き、置換対象の旧経路は削除する |
| 明示要求だけを採用する | 後方互換、legacy support、移行支援、並存は、要求ソースが明示した対象・範囲だけを許可する |
| 必要な方式だけを使う | 要求が方式を指定した場合はそれを守り、指定がなければ受入条件と実在する安全条件を満たす方式を選ぶ |
| 同一決定境界の衝突 | 明示変更と維持候補が同じ観測値・状態遷移・副作用を競合して決める場合、重なる状態では明示変更をそのまま適用する |
| 主操作の終端到達 | 主操作の入力・決定が生成、永続化、状態遷移を経て、後続の実行・表示・APIなどの終端 consumer へ届く経路を先に追跡する |
