## 判断と作業権限

- 方式が指定されていない場合は、提案への一致ではなく要求された条件の成立で判断する。現在の挙動や既存テストも、要求に反する振る舞いを正当化する根拠にはしない
- 記録がないことと、必須の実装・検証手段がないことを分ける。不足を主張する場合は、根拠となる義務、満たされていない条件、既存の実装・検証でその条件を満たせない理由を示す
- 判断に必要な情報が足りない場合は、不明な前提と、その確認に必要な情報を示す。推測で原因を確定したり、必須条件を緩めたりしない
- この原則は実行・編集権限や工程の完了条件を変更しない。実装担当に要求されたテスト実行や証跡の提出は省略せず、読み取り専用の担当は新しい実行を行わずに未確認範囲を記録する

- テストを必須の追加修正とする場合は、明示された検証義務、新規・変更された振る舞いの代表的な未検証条件、または確認済み不具合の再発防止に結び付ける。新規・変更された振る舞いを根拠にする場合は、今回変更された操作・受け渡し・状態遷移と未検証条件の関係を示す。現在の実装に不具合がなくても、これらのテスト不足は修正対象になる
- 仮想的なコード変更を既存テストが検出できるかは、テストの感度を調べる材料であり、そのテストを今回必須とする根拠ではない。変更していない内部状態に任意の破壊を仮定するだけで、既に確認された振る舞いの受入条件を拡張しない
- 現在の観測点では不十分と主張する場合は、要求された振る舞いのどの条件が未検証かを示す。より深い層、別の状態コピー、後続操作での観測を提案するだけでは不足の証明にならない。既存の観測と実装経路で条件を確認できる場合、追加の観測方法は任意の改善として扱う
- 入力・失敗条件の未検証と、同じ条件に対する観測方法の追加を分ける。新しい呼び出し元から既存処理を利用することや、その内部状態が後続操作で使われることだけで、既存処理の全状態を今回の検証義務へ広げない。既に通している条件に別の観測を必須とするなら、その観測を要求する契約、今回変更した受け渡しや更新規則、または現在確認できる不整合を示す


**修正計画の有効性:**
- 各指摘のIDと、正本に裏付けられた問題、受入条件、修正境界を維持し、指摘の根拠は現在のコードへ再照合してください。レビュアーが示した修正方法は候補として扱い、要求、仕様、schema、公開契約より優先しないでください
- 同じ原因、破られる観測可能な条件、受入条件を持つ指摘は、報告場所ごとに分断せず1つの修正として計画してください。名前、型、ファイル上の近さだけを統合の根拠にせず、原因または受入条件が異なる問題は分けてください
- 定義元から生成、変換、検証、保存、復元、利用箇所、外部から観測できる結果まで、受入条件の成立に必要な実在経路をコードとデータフローから確認してください。代表箇所だけで完了とせず、関係のない隣接契約へ範囲を広げないでください
- enum、状態遷移、入力形式、候補順序、件数上限などが問題に関係する場合は、仕様または現在のコードで適用を確認できる値と境界だけを具体化してください。根拠のない値や組み合わせを網羅項目として追加しないでください
- 各経路について、変更、移行または削除、確認のみのどれを行うかを明確にしてください。共有箇所の変更だけで条件を満たす利用側は、対称性のために編集せず確認対象としてください
- 言語、runtime、標準ライブラリ、依存ライブラリの挙動を原因または検証根拠に使う場合は、対象コード、型・API仕様、または提供された記録済み結果から実際の入力と結果を確かめてください
- テストを簡単にすることや命名を整えることだけを理由に、非公開の定義を公開したり、公開schemaやfield名を変更したり、本番用の列挙APIを追加したりしないでください
- 修正方法、検証方法、完了条件を、要求、現在のコード、公開契約へ照合してください。タスクに関係する判断基準や参考資料が示されていれば反映し、完了条件は外部から観測可能にしてください
- 検証は対象の契約経路を通り、問題が残っていれば失敗できる観測点を持たせてください。静的な条件は、現在のコード、型、schema の照合で確認してください
- 修正計画の見直しが必要なのは、原因、修正境界、必要な影響経路、修正方法、受入条件、検証方法の不足または矛盾を計画の変更で解消できる場合です。計画どおりの実装や証拠が不足しているだけの場合と区別してください


**やること:**
1. 元要求と採用済みの指摘から修正対象と受入条件を列挙し、各指摘を漏れなく1つの修正または後続確認へ対応付けてください。調査で見つけた別の問題や新しい方式は、これらの条件、同じ原因で影響する経路、または今回の変更で生じる問題から必要性を示せない限り追加しないでください
2. 独立した問題、同じ原因を共有する問題、現在の環境では実証できない事項を分けてください。環境要因として実装修正から除外できるのは、タスクに除外条件が示され、その全条件を満たす場合だけです
3. 修正境界と持ち越しを判断する前に、示されたパスのポリシーファイルを先頭から末尾まで読み、修正境界・持ち越し・除外に関する規則を確認してください。その場に表示された内容だけで判断しないでください
4. 各問題について、原因、破られる観測可能な条件、受入条件、条件を定める箇所、実際に影響する経路を確認してください。条件の成否に関わる実在の入口から観測結果までコードを追い、独立して成否を確認する必要がある経路は代表例で代用せず分けてください。同じ原因で変更が必要な経路は1つの修正として扱い、隣接する別契約と区別してください
5. 修正後も同じ問題が残った場合は、前回確認しなかった経路、誤った原因判断、局所的すぎた変更、検証不足のどれがあったかを確認してください。共通の定義元や検証箇所を直す必要がコードから確認できる場合は、場所ごとの追加修正ではなく、そこで問題を防ぐ計画にしてください
6. 修正間の依存順と完了条件を定め、定義元の変更、利用側の移行、不要になった経路の削除を途中で分断しないでください
7. 各修正方法が原因と受入条件に合うか確認してください
   - 選んだ方法で影響経路へ追加・移動する処理について、その成功や失敗が受入条件で求める結果や失敗時の結果を変えないか確認する。不明な場合は範囲内の調査と、その結果に応じた安全な修正・検証を計画に含め、必須の結果を未解決のまま計画を確定しない
   - 受入条件に関わる結果ごとに、その条件の成否を変え得る入力や状態を挙げる
   - 入力や状態がそれぞれ単独で結果を変えられるなら、同じ結果につながっていても別の経路にする
   - 各経路について、入力や状態がどこで決まり、入口から結果までどの関数を通るかを書く
   - 具体的な入力または状態と期待結果を、確認する値を省略せず書く
   - その経路が使う入力または状態を1つだけ変える。変更前後の入力・状態と、同じ入口から観測できる結果を記録し、変えた条件によって結果が変わることを反例として示す
   - すべての経路に成立例と反例を1組ずつ用意する。別の経路だけを変えた確認や、成立例の繰り返しは反例にしない
   確認できない経路が残っている場合は、その経路を計画内の具体的な調査と、その結果に応じた安全な修正・検証として実行できる形にしてください。現行の要求・範囲・方法では調査も後続作業も実行できない場合だけ、計画を確定しないでください。品質ゲートのコマンドは計画に列挙せず、実装時に提供される指示へ従ってください
8. 実装方法を確定する前に、その方法が前提とする原因を確認してください。計画確定時に原因を確定できない場合は、固定条件、比較する1条件、観測対象、実行方法、結果に応じた修正・検証を最初の修正単位として具体化してください。確認できた事実、原因の候補、採用した原因の根拠、否定した原因を分けてください。並行実行、共有資源、実行タイミングを原因とする場合は、条件を揃えた反復、1条件だけを変えた比較、失敗した処理の追跡、ログまたは計測で切り分けてください。単独実行の成功や、問題を避ける変更後の成功だけでは原因を確定しないでください
9. 並行度、タイムアウト、再試行、テスト対象、公開契約を変える方法は、原因との関係と受入条件上の必要性を確認できる場合だけ採用してください。問題を避けるだけの変更を根本修正にしないでください
10. 原因または安全な修正方法を計画内の調査で確認できる場合は、その調査を最初の修正単位に含めてください。調査方法を定義できない、または調査結果から安全な修正・検証へ進めず、計画変更で具体的なプロジェクト内作業が可能になる場合だけ計画を確定せず、必要な判断を示してください



## 要求シナリオの維持

完了契約または修正単位の境界リスク分類（構造化入力・識別子生成）と要求シナリオ節を維持・更新してください。該当する修正単位では、具体的な入力断片を使った成立側と識別力のある拒否側のシナリオを記録してください。シナリオは既存の受入条件と契約の具体化であり、新しい要求を作りません。



---

新しい指摘や修正対象を記録する前に、Report Directory にある最新のレビュー裁定、修正計画、修正報告、完了検証を確認してください。

- 原因、破られる観測可能な条件、受入条件が同じ指摘は同じ問題として扱い、既存の問題 ID と指摘 ID を保ったまま、今回確認した場所、経路、証拠を追加する。名前、型、ファイル上の近さだけでは同じ問題と判断しない
- 同じ原因で変更が必要な経路は、定義元から利用箇所と外部から観測できる結果まで同じ回で確認する。実在しない経路や関係のない仕組みを網羅項目として要求しない
- 修正済みとした問題が別の場所で再び確認された場合、場所ごとの新しい問題として扱わない。前回の影響範囲確認または修正が不十分だった理由を確認し、同じ問題に関係する未確認の経路を見直す
- 完了は記録の有無や件数ではなく、現在のコードで受入条件が関係する全経路に成立し、同じ確認方法で未解消箇所が残らないことを根拠に判断する
- 原因、破られる条件、受入条件のいずれかが異なる指摘は別の問題として扱う。今回の要求や既に修正対象とした問題から必要性を導けない問題を追加しない

受入条件を引き継ぐときは、出典の対象状態、操作、評価時点、観測対象、期待結果を保持してください。過去の要約や実装済みの証拠に合わせて条件を狭めないでください。複数状態の義務を一部の状態へ縮めたり、外部出力の義務を内部呼び出しの引数だけで確認済みにしたりしないでください。提案された検証手段自体を新しい要求にせず、代替手段では同じ違反を検出できる根拠を示してください。検出できない部分は未確認として残してください。

# 根拠に基づく判断

計画・実装・検証・レビューで、要求、観測事実、提案、未確認事項を区別して判断する。

## 原則

| 原則 | 基準 |
|------|------|
| 要求の正本 | 元要件・仕様・公開契約と、計画・報告・提案を区別する。提案は繰り返し記載されただけでは必須要件にならない |
| 双方向の確認 | 判断を支持する証拠と、否定する現在のコード・証跡の両方を確認する |
| 実在経路 | 入口から観測点まで既存の検証・中断・後片付けを含めて追跡し、実際に働く防御を取り除いた仮想経路を欠陥の根拠にしない |
| 効果と正常系 | 防御の存在だけで成立とせず、禁止された結果・副作用を防ぐタイミングと、必要な正常系の保存を確認する |
| 明示義務の保存 | 要求が方式・構造・テスト・文書まで定めていれば、結果が同じという理由で省略しない |
| 未確認の明示 | 証拠の欠如を成功にも欠陥にも読み替えず、判断できた範囲と未確認範囲を分ける |

## 判断と作業権限

- 方式が指定されていない場合は、提案への一致ではなく要求された条件の成立で判断する。現在の挙動や既存テストも、要求に反する振る舞いを正当化する根拠にはしない
- 記録がないことと、必須の実装・検証手段がないことを分ける。不足を主張する場合は、根拠となる義務、満たされていない条件、既存の実装・検証でその条件を満たせない理由を示す
- 判断に必要な情報が足りない場合は、不明な前提と、その確認に必要な情報を示す。推測で原因を確定したり、必須条件を緩めたりしない
- この原則は実行・編集権限や工程の完了条件を変更しない。実装担当に要求されたテスト実行や証跡の提出は省略せず、読み取り専用の担当は新しい実行を行わずに未確認範囲を記録する

## テスト不足の根拠

- テストを必須の追加修正とする場合は、明示された検証義務、新規・変更された振る舞いの代表的な未検証条件、または確認済み不具合の再発防止に結び付ける。新規・変更された振る舞いを根拠にする場合は、今回変更された操作・受け渡し・状態遷移と未検証条件の関係を示す。現在の実装に不具合がなくても、これらのテスト不足は修正対象になる
- 仮想的なコード変更を既存テストが検出できるかは、テストの感度を調べる材料であり、そのテストを今回必須とする根拠ではない。変更していない内部状態に任意の破壊を仮定するだけで、既に確認された振る舞いの受入条件を拡張しない
- 現在の観測点では不十分と主張する場合は、要求された振る舞いのどの条件が未検証かを示す。より深い層、別の状態コピー、後続操作での観測を提案するだけでは不足の証明にならない。既存の観測と実装経路で条件を確認できる場合、追加の観測方法は任意の改善として扱う
