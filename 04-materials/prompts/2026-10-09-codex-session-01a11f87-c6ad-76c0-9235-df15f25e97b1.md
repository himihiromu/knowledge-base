**共通の契約経路分析**

観測可能な不変条件、その成立を保証する担当箇所、同じ原因で変更される理由が一致する経路は、物理的なコード位置、ファイルパス、症状、利用者、外部境界、最終結果が異なっても、同じ問題としてまとめて扱ってください。いずれかが異なる場合だけ、別の問題として扱ってください。

実在する経路を `owner / definition -> producer -> transform / normalize / validate -> persist / transfer / restore -> consumer -> exception / retry / fallback / parallel -> terminal / API / observability` として記述し、該当しない段階を作らないでください。

ファイル名や関数名の一覧だけを経路の根拠にしないでください。入口から各利用箇所へ値や状態が渡る呼び出し、引数、返り値、保存・復元の接続をコードで確認し、接続を確認できない候補は未確認または対象外として区別してください。

確認した経路ごとに、不変条件の成立に関与して変更が必要か、接続しているが既存契約を保持すべきか、別の不変条件または担当箇所に属するかを平易な言葉で区別してください。

この分析だけを理由に確認範囲を広げないでください。探索、指摘、編集は、現在の要求と提示された確認範囲から必要性を導けるものに限ってください。


要求または受入条件が変更する不変条件ごとに、担当箇所、実在する経路、各経路で必要な変更または保持条件を計画へ反映してください。初回計画では必要な各経路を実装義務と直接証拠へ対応付けてください。再計画では、失敗した担当箇所、経路、境界、証拠の仮定を示し、同じ失敗方法を反復しない計画へ置き換えてください。

この手順ではコードやテストを編集せず、finding の追加・棄却や完了判定を行わないでください。

**変更契約の追跡（実装タスクでは必須）:**
1. 要求、計画、変更対象外として維持する観測可能な既存動作から、今回の完了条件を特定してください。ワークフローが契約IDを提供する場合は意味を維持し、実装箇所や作業順のためにIDを増やさないでください。
2. 後段で新しい完了義務が見つかった場合は、要求または変更した契約との因果関係を示してください。根本原因や設計を変える場合は既存IDの意味を書き換えず、再計画を要求してください。
3. 完了証拠は、各変更契約を直接観測できるテストまたは再現可能な確認結果へ対応させてください。広いテストスイートの成功だけを個別契約の証拠にしないでください。

**存続する実体の状態が変わる要求:**

要求が、特定の変化（入力、環境、設定、接続状態などの変化）を名指しし、その変化の後もその時点の状態に合わせて振る舞うことを求め、かつその変化をまたいで同じ実体（画面、プロセス、接続、セッション、キャッシュなど）が存続する場合、契約の観測単位はその実体の寿命に合わせる。既存の振る舞いを維持する要求や、変化を名指ししない要求は、それだけではこの契約にならない。
- 同じ実体の上で、変化前の状態 → 変化 → 変化後の状態を一続きに観測することを完了証拠にする。条件だけ変えて別の実体を作り直した観測は、この契約の証拠にならない
- 変化前にその実体が作った成果物（出力済みの表示、計算済みの結果、保持している一覧や接続状態など）も追従の対象に含める。変化後に新しく作るものだけを対象にし、変化前の成果物を旧状態のまま残す読み替えをしない
- 計画では、存続する実体を特定し、変化に反応できる構造か（一度だけ作る、初回だけ計算する、キャッシュする構造は反応できない）を確認する。反応できなければ、その構造の変更を計画に含める
- テストで観測できる実体を、実環境での手動確認だけに送らない。該当する契約があるのに、計画の「状態・所有権」やテスト報告の「連続実行・所有権・並行性」を「該当なし」にしない
- 変化をまたいで存続する実体がない要求（入力から出力への変換、呼び出しごとに新しく作る結果、プロセスを作り直してから読み込む永続化）や、変化を名指ししない要求には、この軸を持ち込まない


**要求ソースの規律:**
- 目的・制約・受入条件を定められるのは、ユーザー指示、タスク指示書、そこで要件資料として指定されたソースだけです。現行コード、作業中の差分、テスト、レビュー報告、以前の応答、設計・品質上の参考資料は、現状の証拠、設計制約、または提案であり、それだけを根拠に新しい要求を作らないでください
- 分解した要件と完了契約には由来を付けてください。明示要求はソース箇所を示し、暗黙要求はそれがないと成立しない明示要求と理由を示し、維持事項は変更対象外にある観測可能な既存契約の証拠を示してください。契約置換では、変更対象外の既存契約、現行利用側の移行、旧契約の支援対象を別々の要件・完了契約として記録し、支援対象には要求ソースの明示箇所と対象・範囲を対応付けてください。いずれにも該当しないものは設計判断として扱い、要件や完了契約へ混ぜないでください
- ソースが複数の方法を許容している場合、方式を選ぶ前に許容集合全体を要件上で維持してください。名前が挙がった各選択肢に加え、「または同等の仕組み」のような開放選択肢も残し、列挙された方式だけへ暗黙に狭めないでください。調査後に一つを選んでも、選択理由は設計判断として記録し、選ばなかった方法の排除や選んだ内部構造を新しい受入条件にしないでください
- 採用した設計判断は実装アプローチを導いても、明示要求、不可欠な直接導出、または変更対象外として維持する既存契約でない限り、要求IDや完了契約IDを付けないでください
- 許容された複数案から一案を選んだ場合、完了契約にできるのは「許容集合を逸脱しないこと」と明示された維持範囲だけです。選んだ案を、維持要求が及ばない入力・経路まで固定する独立契約にしないでください
- 維持義務が特定の入力、モード、状態、または入口だけに適用される場合は、その境界を明示してください。要求ソースが選択肢を開いたままにしている別の範囲へ、現行動作や採用案を拡張しないでください。契約を適用範囲ごとに分け、許容集合が維持される範囲を示してください
- 型、ヘルパー、ファイル分割、削除、改名などの内部構造は、ソースが指定するか、観測可能な要求を成立させるため不可避な場合だけ完了義務にしてください
- 優先順位、既定値、設定形式、識別子、エラー時動作、初期化・再試行などのライフサイクルは、実装に決定が必要という理由だけで要求にはなりません。要求ソースに指定がなければ、確認事項または理由付きの設計判断として扱い、要求の由来を捏造しないでください
- 最終化する前に、要件と完了契約を一行ずつ再監査してください。要求ソースの記述、不可欠な因果、または変更対象外として維持する既存契約の証拠を示せない行は、要件・完了契約から設計判断または確認事項へ移してください

## 要求シナリオの計画

完了契約を確定する前に、各契約を次の境界リスクに照らして分類してください。

- **構造化入力**: 同じ字面が位置・文脈によって対象/非対象になる入力の分類・変換（コードフェンス、リテラル、コメント、引用、エスケープ領域の区別が結果を変える）
- **識別子生成**: 生成する識別子・連番・名前が、既存本文・保存済みデータ・同一処理内の他の生成物と名前空間を共有する

該当する契約では、対象領域と非対象領域（または既存名前空間と衝突しうる既存値）を具体的な入力断片で固定し、「要求シナリオ」欄に正負ペアのシナリオを書いてください。

構造化入力クラスでは、対象書式のファミリに属する変種（区切り・フェンスの別記法、入れ子、閉じ忘れ）を列挙し、各変種が既存契約で対象・非対象のどちらに属するかを固定した上で、非対象となる代表変種を負例シナリオに含めてください（変種が多い場合は1シナリオの Given に And で束ねてよい）。識別子生成クラスでは、数値境界（巨大値・非数値）か既存名前空間との衝突のうち、既存契約に照らして拒否・回避が定まる側の負例を1本含めてください。

シナリオは既存の完了契約の具体化であり、新しい要求を作りません。どの契約も該当しない場合は、「対象外 — 該当する完了契約なし」と1行記してください。

- 現在の観測点では不十分と主張する場合は、要求された振る舞いのどの条件が未検証かを示す。より深い層、別の状態コピー、後続操作での観測を提案するだけでは不足の証明にならない。既存の観測と実装経路で条件を確認できる場合、追加の観測方法は任意の改善として扱う
- 入力・失敗条件の未検証と、同じ条件に対する観測方法の追加を分ける。新しい呼び出し元から既存処理を利用することや、その内部状態が後続操作で使われることだけで、既存処理の全状態を今回の検証義務へ広げない。既に通している条件に別の観測を必須とするなら、その観測を要求する契約、今回変更した受け渡しや更新規則、または現在確認できる不整合を示す
