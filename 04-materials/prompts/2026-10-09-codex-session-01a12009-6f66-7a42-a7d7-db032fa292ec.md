# 根拠に基づく判断

計画・実装・検証・レビューで、要求、観測事実、提案、未確認事項を区別して判断する。

## 原則

| 原則 | 基準 |
|------|------|
| 要求の正本 | 元要件・仕様・公開契約と、計画・報告・提案を区別する。提案は繰り返し記載されただけでは必須要件にならない |
| 双方向の確認 | 判断を支持する証拠と、否定する現在のコード・証跡の両方を確認する |
| 実在経路 | 入口から観測点まで既存の検証・中断・後片付けを含めて追跡し、実際に働く防御を取り除いた仮想経路を欠陥の根拠にしない |

| 明示義務の保存 | 要求が方式・構造・テスト・文書まで定めていれば、結果が同じという理由で省略しない |
| 未確認の明示 | 証拠の欠如を成功にも欠陥にも読み替えず、判断できた範囲と未確認範囲を分ける |

- 記録がないことと、必須の実装・検証手段がないことを分ける。不足を主張する場合は、根拠となる義務、満たされていない条件、既存の実装・検証でその条件を満たせない理由を示す
- 判断に必要な情報が足りない場合は、不明な前提と、その確認に必要な情報を示す。推測で原因を確定したり、必須条件を緩めたりしない

- 現在の観測点では不十分と主張する場合は、要求された振る舞いのどの条件が未検証かを示す。より深い層、別の状態コピー、後続操作での観測を提案するだけでは不足の証明にならない。既存の観測と実装経路で条件を確認できる場合、追加の観測方法は任意の改善として扱う
