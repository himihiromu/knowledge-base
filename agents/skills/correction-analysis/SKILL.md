# 作業修正時の原因特定・変更箇所判断

作業の修正を求める指摘を原因から整理し、既存のルール・知識・手順・スクリプトのどこに変更を掛けるべきかを判断するスキル。

## 目的

指摘を1件ずつ確認し、原因を仮分類して、複数回の指摘から傾向を分析する。根拠と適用範囲を確認し、変更先（00のルール・02の知識・個別のスキル・スクリプト）を判断する。単発の指摘から恒久ルールを断定しないための手順。

## 使う場面

- 作業の修正を求める指摘・失敗・確認事項を受け取ったとき。
- 指摘の原因が、既存の手順・ルール・知識・スクリプトのどこにあるか分からないとき。
- 同じ種類の指摘が繰り返されていないかを確かめてから、ルールや知識を変えたいとき。

## 入力

- 修正を求める指摘1件以上。出典（ユーザーの発言、レビュー、実行結果など）と、問題が現れた作業・ファイルが分かるもの。
- 指摘を受けた作業の手順、またはその対象ファイル。

## 原則

- 単発の指摘を恒久ルールとして断定しない。知識化は反復と適用条件、ルール化はユーザーが明示した常時適用の意思に基づく。
- 将来の知識・ルールへの一般化は、根拠が揃うまで保留する。ユーザーが今回依頼した修正の実行は別に判断する。常時適用の明示がある場合は[知識ライフサイクル](../knowledge-lifecycle/SKILL.md)に従う。
- 原因を推測で確定しない。分類は仮分類として残し、確認できていない事項は未確認と書く。
- 手順内の例は架空の例である。架空の例を、ユーザーの実際の指摘や好みとして `04-materials/` や `02-knowledge/` に保存しない。

## 手順

1. **原文と分析を分ける**: 04の既存原文を参照し、指摘の発言日時、対象の作業・ファイル、原文へのリンクを確認する。指摘の要旨、仮の原因候補、分類、分析の確認日は作業報告へ記録する。保存が依頼範囲にある場合は03のテーマ別分析レポートを使う。既存原文を再登録せず、分析・仮分類を04へ書き込まない。[共通の配置規定](../../../00-rules/workflow.md)を参照先のスキルにも適用する。
2. **原因を仮分類する**: 指摘ごとに次の5分類の候補を仮付けする。断定せず、あとで追記してよい。
   - 既存手順・規則の未参照: 手順やルールはあるが、使われていない。
   - 手順・規則の欠落: やるべきことがどこにも書かれていない。
   - 環境・前提の違い: 手順どおりでも、環境や前提が違うために起きている。
   - 判断基準（好み）の未記録: どちらを望むかが記録されておらず、都度判断が揺れている。
   - 実装・文書の不具合: 手順・文書・コードそのものの誤り。
3. **スクリプト化できるか判断する**: 指摘の検出や修正が、機械的な検査・変換として確定できるなら[scripts](../../../scripts/README.md)の記録規定に従って追加を提案する。確定できない場合は自動化を保留し、手順1の記録を続ける。
4. **傾向を分析する**: [知識ライフサイクルの数え方](../knowledge-lifecycle/SKILL.md)に従い、同一セッションの再指摘も含め、指摘回数とセッション数を分ける。同じ判断基準への反復と、その作業での重要度、再利用できる適用範囲を確認する。複製・引用・説明だけの補足は加算しない。分析は作業報告または03へ記録する。
5. **変更対象を判断する**: 根拠と適用条件が確認できた知識候補、または常時適用が明示されたルールについて、変更先を選ぶ。お試しで成果物を見てからユーザーが判断する依頼なら草案を提示する。
   - 00-rules: 複数の作業に共通する運用ルールの不足・誤り。
   - 02-knowledge: 再利用する判断基準・好みの未記録。
   - agents/skills: 対象の作業手順そのものの不足・誤り。
   - scripts: 機械的な検査・変換で防げるもの。
   変更するときは既存メモとの重複・矛盾を先に確認し、出典・確認日・変更理由を残す。
6. **確認して報告する**: 変更後に指摘が解消されること、関係するファイルの確認日が更新されていることを確認する。変更したファイルと残った未確認事項を報告する。

## 出力先

- 指摘の原文: 04の既存資料を参照する。
- 指摘の解釈と傾向分析: 作業報告。保存する場合は03のテーマ別分析レポート。
- 変更の反映先: 00-rules、02-knowledge、agents/skills、scripts のいずれか（手順5の判断による）。
- 実施したタスクの状態: [05-todo](../../../05-todo/README.md)の該当項目を更新する。

## 確認方法

- 記録した各指摘に出典と確認日が残っていること。
- 根拠不足の指摘を知識・ルールへ一般化していないこと。ユーザーが明示した常時適用は、その対象範囲を記録していること。
- 原文は04、分析は作業報告または03へ分け、指摘回数・セッション数・適用範囲を追えること。
- 変更した場合、変更先が手順5の基準に合い、既存メモとの重複・矛盾を確認した後に実施していること。

## 例（架空の指摘。実在の指摘・好みではない。このまま保存しない）

```
- 確認日: 2026-09-30（架空の例）
- 出典: 架空のレビュー指摘
- 対象の作業・ファイル: 02-knowledge へのメモ追記
- 指摘内容: 追記したメモに出典が書かれていない
- 仮の原因候補: 出典の書き方を案内する手順が無い
- 分類: 手順・規則の欠落
```

この例は手順の説明用であり、ユーザーの実際の指摘や好みとして `04-materials/` や `02-knowledge/` に保存しない。実際の指摘は手順1の記録先へ、実施した作業として記録する。
