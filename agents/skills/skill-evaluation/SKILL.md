# スキル評価

- 確認日: 2026-10-18
- 状態: 運用手順。AIが根拠付きで仮採点し、ユーザーが妥当性や修正点を確認する。

## 目的

スキル修正の前後で、同じ入力・同じ評価基準で成果を比較できるようにする。
評価のたびに結果・採点理由・未検証範囲を記録し、修正の効果を後から確認できるようにする。

## 機械テストとの範囲

この手順は、ケースを使ってスキルの出力品質をAIが仮採点し、ユーザーが根拠と判定を確認するためのもの。機械テストは、スキル文書が参照するリンクなど、決定的に検査できる構造上の契約を確認する。たとえば `scripts/test/filter-related-knowledge.test.mjs` は、対象スキル文書の出典リンクと相対リンク先を検査する。このテストはその対象スキルのリンク契約を確認するもので、スキル出力の品質評価ではない。機械テストは評価基準の採点やモデル出力の品質判定を行わず、AIの仮採点やユーザー確認も機械テストの代わりにはならない。

## 使う場面

- スキルを修正する前に、修正前の成果を評価して記録するとき。
- 修正後に同じケースで再評価し、差分を確認するとき。
- 対象スキルが未実装のときも、ケースに同梱した成果サンプルで評価経路を確認するとき（[example ケース](cases/example/case.md)）。

## 入力

評価のたびに次の3点を指定する。機構に固定値はなく、差し替えて使う。

| 入力 | 内容 | 例 |
| --- | --- | --- |
| 対象スキル | `agents/skills/<スキル名>/SKILL.md` のパス。未実装のときは「なし（成果サンプルを使う）」 | `agents/skills/knowledge-prompts/SKILL.md` |
| ケースID | `cases/` 配下のフォルダ名 | `example` |
| 版ラベル | 今回の成果に付ける自由記述のラベル | `修正前`、`v1` |

成果は対象スキルを実行して作る。対象スキルが存在しない場合は、ケース定義が示す成果サンプルを評価対象に読み替える。

評価開始時に、次の比較条件も記録する。版ラベルだけを版の根拠にしない。

- 対象スキルと参照資料、ケース定義・評価基準、入力資料の取得元と版。Git管理ならパスとコミットを使い、未コミット変更があれば差分または使用した内容のコピーも残す。Git管理外なら保存した内容やハッシュなど、同一性を確認できる根拠を残す。
- 結果に影響する環境条件。使用ツールの版、モデル・設定、既存タスクの登録状態など、今回関係する条件に絞る。

確認できない条件は「不明」と理由を残し、比較への影響を未検証範囲に記載する。成果サンプルを使う場合は、対象スキルの版を「該当なし」としてサンプルの版を記録する。

## 配置とリンク

- 評価手順はこの `SKILL.md` に置く。
- 入力ケースと、そのケースだけで使う期待例・サンプル出力は `agents/skills/skill-evaluation/cases/<ケースID>/` に置く。ケース定義からサンプルへ相対リンクする。
- 評価結果は `03-output/skill-evaluation/` に置く。結果から採点対象と比較対象の旧結果へ相対リンクし、ケース内のサンプルからケース定義へ相対リンクする。
- 機械テストはプロジェクトのテスト配置に置き、対象のスキル文書へのリンクを保つ。この評価用ケースを機械テストの期待値として複製しない。
- 手順書からケースへ、結果READMEから手順書と結果例へ、それぞれリポジトリ内の相対リンクを張る。

現行のケースとサンプルは `cases/example/` に分けてあり、結果は `03-output/skill-evaluation/` にある。ケースとサンプルはこの評価手順が所有する入力・採点基準のため、この配置を維持する。共通の機械テスト領域へ移す必要はない。

## 手順

1. **ケースと条件を確認する**: `cases/<ケースID>/case.md` で入力・実行方法・評価基準を読み、使用する版と環境条件を記録する。
2. **成果を用意する**: 対象スキルの SKILL.md の手順に従い、ケースの入力から成果を作る。対象スキルが存在しない場合は、ケース定義の成果サンプルを評価対象にする。
3. **仮採点する**: [result-template.md](result-template.md) を複製し、基準ごとに判定・根拠・未検証範囲を記入する。採点者と成果作成者が同一かを明記し、ユーザー確認は「未確認」とする。機械検査の結果とAIによる意味の判断を区別する。
4. **比較する**: 同じケースの旧結果について、入力・評価基準・環境条件の一致と、比較するスキルの版を確認する。比較可能なら旧結果への相対リンク、基準ごとの判定差分と採点理由の違いを記入する。旧結果がなければ「初回記録」、条件が異なるか確認できなければ「比較不可」と理由を残す。過去の会話を参考にした振り返りは比較結果と区別し、改善効果の証明に使わない。
5. **保存する**: 比較内容まで記入してから、出力先へ `YYYY-MM-DD-<対象>-<版ラベル>.md` で保存する。`<対象>` は対象スキル名、成果サンプルで評価するときはケースID。同名ファイルがあれば上書きせず、`-2`、`-3` のように末尾へ連番を付けた別ファイルにする。保存済みの結果ファイルは後から編集しない。
6. **ユーザーに提示する**: 実施手順・成果・仮採点の根拠・未検証範囲を示し、ユーザーが妥当性や修正点を確認する。確認が得られたら、元の結果への相対リンク、確認日、ユーザーの判断と修正点を別の確認記録として同じ出力先へ保存する。判定を修正する場合も元の記録を残し、変更理由を記載する。返答がなければ未確認のままとし、AIだけで確認済みにしない。

## 出力先

[03-output/skill-evaluation/](../../../03-output/skill-evaluation/README.md) に結果ファイルを保存する。

## 確認方法

保存後に結果ファイルを開き、次を確認する。

- 必須項目（実行日、対象スキル、版ラベル、ケースID、使用した入力、結果、採点理由、未検証範囲、採点者・成果作成者、比較条件、ユーザー確認の状態）が空欄でない。
- 採点理由が評価基準ごとに書かれ、判定の根拠として読める。
- 未検証範囲に、今回確認できなかった条件とその理由が書かれている。
- 比較対象がある場合、「比較対象の旧結果」のリンクが解決し、条件の一致・相違と基準ごとの差分が読める。比較できなければ理由がある。
- AIの仮採点とユーザーの確認が区別され、確認後の記録から元の結果を参照できる。

配置・言語・リンクの規約は[運用ルール](../../../00-rules/workflow.md)に従う。
