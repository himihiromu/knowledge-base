# 作業に関連するナレッジの絞り込み

作業内容を入力に、02の再利用可能な知識を絞り込み、出典・作業条件・前例を区別して参照するスキル。

## 目的

開発や文書作成などの依頼に対し、適用する知識とその根拠を選び、今回の判断や成果物のどこに反映するかを示す。04の元資料、02の整理済み知識、03の用途別成果物という役割を保ち、作業の要求・手順は別途確認する。

## 使う場面

- 作業を始めるとき、02の知識・判断基準のうち適用するものを絞り込みたいとき。
- 検索の対象と除外を確定してからメモを探したいとき。
- 候補のメモが複数あり、採否と優先順位を決めたいとき。

## 入力

- 作業内容が分かるもの。依頼文、[05-todo](../../../05-todo/README.md)の項目、対象のファイルやパス、作業の目的のいずれか。今回作る成果物と完了条件も確認する。
- 作業内容があいまいな場合は、推測で補わず依頼者へ確認する（[agents.md](../../../agents.md)の「未確認の情報や空欄を推測で埋めない」）。

## 取得する情報の役割と検索範囲

| 役割 | 取得元 | 確認する内容 |
| --- | --- | --- |
| 適用する知識（シルバー） | [02-knowledge](../../../02-knowledge/README.md) | 再利用可能な判断基準・技術メモ。今回の条件で使える箇所を選ぶ |
| 出典（ブロンズ） | 採用候補からリンクされた[04-materials](../../../04-materials/README.md)や一次資料 | 知識を裏付ける元の発言・事実・適用条件。原文と解釈を区別する |
| 作業内容・制約・実行手順 | 現在の依頼、[05-todo](../../../05-todo/README.md)、[運用ルール](../../../00-rules/workflow.md)、[作業手順](../README.md)、[scripts](../../../scripts/README.md)、作業対象ファイル | 今回の要求・完了条件・制約・実行方法。一般的な知識との役割を分ける |
| 前例・成果物（ゴールド） | [03-output](../../../03-output/README.md) | 類似の成果物や評価結果。参考にする箇所と今回との条件差を確認する |

- 作業条件を把握した後、知識の検索は02を中心に行う。他の領域は出典の確認や作業上の不足を補う必要があるときに、役割と確認目的を決めて参照する。毎回すべての領域を横断検索する必要はない。
- 02に該当する知識がなければ「該当なし」と報告する。04や03だけに見つかった内容は出典・前例として示し、整理済みの知識に数えない。知識化が必要なら候補と理由を示し、整理・昇格は[Knowledge ライフサイクル](../knowledge-lifecycle/SKILL.md)に従う。
- 通常の検索では `01-secret/`、`06-storage/`、`99-trash/` を除外する（[agents.md](../../../agents.md)）。
- `01-secret/` は依頼されたときにその範囲で読む。そこにある情報を通常のメモへ転記しない。
- 関係がありそうなのが除外ディレクトリだけのときは、対象を限定して参照するか依頼者へ確認する。
- 候補の列挙には `rg` などを使う。機械的な検査・変換は[scripts](../../../scripts/README.md)に従い、関連性の判断はこの手順が行う。

## 選択基準

1. **テーマと適用条件の一致**: 作業の対象・目的・必要な判断基準と、02のメモの内容が直接関係し、対象環境や適用範囲が今回の条件に合うか。現在の明示的な依頼と異なる知識を優先しない。
2. **本文の確認**: 採用の前に本文を読む。見出しやファイル名だけでは採否を決めない（[agents.md](../../../agents.md)の「タイトルや紹介文から本文の要約を作らない」）。
3. **優先順位**: メモの `状態`（検証済みを未確認より先）を先に見て、次に `確認日` の新しさで並べる。項目は[知識メモの雛形](../../../00-rules/templates/note.md)と[運用ルール](../../../00-rules/workflow.md)が定めるものだけを使い、新しいメタデータを作らない。
4. **未確認・未検証の明示**: 採用したメモが未確認・未検証なら、その旨を明示して使う（[運用ルール](../../../00-rules/workflow.md)の「未検証の手順は未検証と記載する」）。
5. **同点の候補**: 基準で一意に決まらない候補は、無理に絞らず両方を出典付きで示す。

## ナレッジ間の関係候補を確認する

関係は、確認した2件のナレッジ間に相対リンクを置き、判断と根拠をリンク元の本文に記録する。相対リンク先は関係するナレッジであり、リンクを張っただけで関係が確定したとは扱わない。

| 関係 | 意味 | 記録する根拠 |
|------|------|----------------|
| `duplicate` | 同じ内容を実質的に繰り返している | 重複する対象箇所、双方の出典、重複と判断した理由 |
| `related` | 内容は同一でないが、参照すると理解や作業に役立つ | 関連する対象箇所と、どう関係するか |
| `contradicts` | 同じ適用条件で両立しない主張がある | 双方の対象箇所、出典、適用条件、確認日、両立しない理由 |
| `supersedes` | 新しい知識が、明示した範囲で古い知識に代わる | 双方の対象箇所と出典、旧知識が有効だった範囲、新しい知識の適用開始条件、置き換え理由、確認日 |

記録例（項目名と関係の方向を示す形式例。実在のナレッジではない）:

```markdown
## 関連する知識
- 関係: `supersedes`（このメモがリンク先の旧知識に代わる）
- 対象: このメモ「設定 A の既定値」／旧知識への相対リンク（例: `../path/to/old-knowledge.md`）「設定 A の旧既定値」
- 出典: 各メモの出典節を参照
- 適用条件: 新設定は 2026-10-01 以降の構成に適用。旧知識はそれ以前の構成に適用。
- 置き換え理由: 仕様変更を確認したため
- 確認日: 2026-10-02
```

確認時は、Quality CI の重複候補（同一外部URLまたは同一H1）と矛盾候補（同一URLを参照するメモ間の状態差）を、機械的な根拠を示す候補として扱う。これらは意味的な関係の確定ではない。語句や意味の類似から提案する候補も、比較した箇所と提案理由を示し、人が本文と出典を確認する。CI が見つけない関係も検索で見つけた場合は同じ手順で確認する。

1. 候補元と相手の本文、対象箇所、出典、確認日、適用条件を確認する。CI 候補では報告された一致・状態差も記録する。
2. 検討した関係を選び、根拠を両方のメモから追えるよう記録する。確定できない場合は関係リンクを確定情報として追加せず、未確認の提案として作業報告に残す。
3. 人が採否と関係を判断した後でのみ、判断・理由・確認日をメモへ記録し、必要な参照リンクを追加する。関係の記録だけを理由に本文を削除・統合しない。
4. `supersedes` は新しいメモから旧知識への方向を明記する。旧知識は残し、旧情報が有効だった範囲と置き換え理由を旧・新両方の出典とともに追跡可能にする。参照や変更は [Knowledge ライフサイクル](../knowledge-lifecycle/SKILL.md) の手順に従う。

## 手順

1. **作業内容を整理する**: 現在の依頼と該当TODO・対象ファイルから、目的、成果物、完了条件、制約を確認する。適用するルール・実行手順と、知識検索のキーワードを整理する。
2. **02から候補を収集する**: 作業に関係する知識を検索し、本文を読んで選択基準に沿って採否と優先順位を決める。関連する知識がなければ、その結果と不足する情報を明示する。
3. **出典を辿る**: 採用候補の出典リンクから04や一次資料へ進み、今回使う主張の根拠と文脈を確認する。確認できない主張は未確認として扱う。メモの一部の確認を、全体の再検証として報告しない。
4. **必要な補助情報を取得する**: 足りない作業条件や実行方法を05・00・手順・スクリプト等で確認する。前例が必要なら03を参照する。02にない情報を04・03から直接使う場合も、取得元の役割と未検証事項を保つ。
5. **適用方法と参照を示す**: 下記の出力形式で、知識を今回の判断や成果物のどこへ反映するか、出典は何を裏付けるか、作業条件や前例は何の確認に使うかを報告する。関係がありそうでも採用しなかった有力候補には理由を添える。

## 出力形式と参照先

- 絞り込み専用の記録ファイルは作らず、作業の報告・成果物に次の区分で示す。該当する知識がなければ明記し、不要な補助情報の欄は省略できる。
  - 適用する知識: 02の参照先、採用箇所・理由、状態・確認日、今回への適用方法。
  - 出典: 原文・一次資料の参照先、裏付ける知識や主張、今回確認した範囲と未確認事項。
  - 作業内容・制約・実行手順: 要求の出どころ、今回の対象・完了条件、適用するルールや実行方法。
  - 前例・成果物: 03の参照先、参考にする箇所、今回との条件差。サンプルを実運用の検証結果として扱わない。
- リポジトリに保存する成果物では相対リンクを使う。作業コピーや一時ディレクトリの絶対パスを恒久的な参照先にしない。チャットやPRではリポジトリ内のパスと、必要に応じて対象コミットのリンクを示す。別のworktreeや版を参照した場合は、参照した版と正式な配置を明記する。
- 不足・誤り・古い確認日は、根拠とともに修正候補として報告する。修正が依頼範囲に含まれる場合は、[運用ルール](../../../00-rules/workflow.md)に沿って更新し、選定結果とは別に変更内容を報告する。確認日が古いことだけを理由に日付を更新しない。
- ファイルの削除は依頼に従い、削除の代わりに退避する規定に従う。

## 確認方法

- 候補の検索から除外ディレクトリが外れていること。
- 適用する知識が02の本文に基づき、出典・作業条件・前例と区別されていること。02に該当がない場合、その旨が明示されていること。
- 知識の採用理由、状態・確認日、今回への適用方法、出典の確認範囲が追えること。
- 未確認・未検証の内容を使った場合、その旨が報告・成果物に明示されていること。
- 正式な配置と参照した版が分かり、一時作業場所を恒久的な参照先にしていないこと。

## 例（架空の入力・架空のメモ。実在の記録ではない。このまま保存しない）

```text
入力: 開発タスク「GUIアプリAを使える状態にする」
作業内容: 05のTODOで対象環境・完了条件を確認。00のルールと実行手順も確認する。
適用する知識: 02の「GUIアプリの利用条件」（検証済み・確認日 2026-10-01）を採用。
  今回への適用: インストールに加え、デスクトップから起動できることを確認する。
出典: 上記メモが参照する04の会話で、起動経路への要求を確認した。
前例: 03の別アプリの導入結果を参考にする。ただし対象環境が異なり、検証結果は流用しない。
不採用: 02のCUI専用メモは対象が異なるため採用しない。

02に該当がない場合:
適用する知識: 該当なし。
作業内容: 今回の明示的な依頼とTODOに沿って進める。
出典・前例: 必要な原資料や既存成果物は補助情報として示す。知識化は別途判断する。
```

この例は手順の説明用であり、架空のメモや入力を `02-knowledge/` などへ保存しない。
