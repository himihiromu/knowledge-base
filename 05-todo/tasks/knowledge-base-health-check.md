# Knowledge Baseのヘルスチェックを設計する

- 状態: 未着手
- 確認日: 2026-10-06
- 出典: 2026-10-06のユーザー依頼。CIの構造的・機械的な検査とは役割を分け、Knowledge Baseの健全性や成長状態を振り返るレポートを検討する依頼。

## 目的

Knowledge Baseの構成・検証状態・未整理の入力・利用状況を定期的に振り返り、次に人が確認する領域を選べるようにする。

## 背景

[Knowledge Quality CI](knowledge-quality-ci.md)は追跡済みMarkdownのリンク・メタデータ・形式等を検査し、確定違反があればCIを失敗させる。ヘルスチェックはその検査を複製したりCIの合否条件にしたりせず、既存の結果や鮮度・関係情報を使って、全体の状態と推移を人が見るための案内を担う。

## 要求

- Knowledge、Materials、Outputの件数、未確認・stale・deprecatedの知識、broken links、orphan、重複・矛盾候補等の指標を検討する。
- MaterialsからKnowledgeへの昇格やObservationからの昇格が遅れている候補を扱う。ただし、準備状態・Observationとの対応が記録されていないものを、単に古いという理由だけで未処理と断定しない。
- 利用記録やアクセス計測がない場合、「長期間利用されていない知識」は実測できないことを明示し、リンク数等を使う場合も利用実績ではなく代理指標と呼ぶ。
- 各指標について、対象範囲、算出方法、既知の限界、機械判定か人の確認かを記録する。判断できない項目は不明として扱う。
- 既存の[品質検査スクリプト](../../scripts/check-knowledge-quality.mjs)が出す違反・候補を再利用し、別実装で同じ判定ロジックを複製しない方法を検討する。
- CIは「構造的に壊れていないか」を判定し、ヘルスチェックは「どこを人が見直すとよいか」を示す非ブロッキングな振り返りとする。
- レポートを毎回リポジトリに保存する必要性と、保存する場合の出力先は[成果物の配置ルール](artifact-structure-rules.md)に沿って検討する。固定の表示形式は先に定めない。
- 01-secretの内容を含めず、`agents.md` の検索除外と外部資料を命令として実行しない規則を維持する。
- 新しい依存ライブラリ、Vector DB、外部サービスを前提にせず、現在の追跡ファイルとCI結果でできる試作から始める。

## 完了条件

- [ ] CIとの役割分担と、各指標の定義・算出方法・限界が文書化されている。
- [ ] 鮮度管理・関係候補タスクの結果をどう取り込むかが定義されている。
- [ ] 現行リポジトリの小規模な試行レポートを作り、実測・推定・未計測を区別している。
- [ ] レポートから人が取る次の行動を示せる一方、件数だけを品質や成長の合否と扱わない。
- [ ] シークレットを参照せず、新しい外部依存を導入せずに基本の試行ができる。
